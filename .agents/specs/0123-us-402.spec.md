# Specification — add new skill for enhancing refinement ws-spec-translate-to-human

## Description

The pipeline produces agent-facing artifacts (`step-NN-{slug}.spec.md`, plan, review, testing reports) that are optimized for autonomous execution, not for a human who wants a short, ordered runbook to implement or manually verify the feature. Today that human-facing view is produced ad hoc (the personal `traduzir-spec` skill shown in the issue), outside the harness and disconnected from the workflow's refinement phase.

This spec adds a packaged skill, **`ws-spec-translate-to-human`**, that emits a **parallel human companion** beside the step artifact it translates:

```text
{plansDir}/{slug}/step-NN-{slug}.spec.md              (agent spec, already exists)
{plansDir}/{slug}/step-NN-{slug}.spec-translated.md   (human runbook, new)
```

The companion is a numbered runbook with three parts — **Implementation**, **UI Test**, and **Out of scope** — where every acceptance criterion in the source spec becomes either an implementation step or a UI-test step, UI labels are mapped to the real system (menu/screen/button/status/entity), and scope boundaries are preserved verbatim in intent. It never implements code and never rewrites the agent spec.

The skill is invoked during the **refinement phase** (plan write / plan interview), and may also be invoked standalone. Before writing, it gathers context from the workflow's own artifacts and the project knowledge sources, and when a genuine question blocks a faithful translation it asks the operator through `user-gate` (except in `autoMode`, where it records the open question instead of prompting):

- `step-NN-{slug}.spec.md` (agent spec of record / workflow copy)
- `step-00-{slug}.issue.json` (original tracker snapshot, audit-only)
- the original US/issue from the SCM provider
- `{memoryDir}/MEMORY.md`, the changelog file, `README.md`, project docs, and `AGENTS.md`/hub rules
- the optional spec-memo vault (when memory integration is enabled)

Architecture touchpoints: a new `ws-spec-translate-to-human` skill package (SKILL.md + optional helper script + example), the refinement step wiring in `ws-spec-to-pr` / `ws-spec-to-pr-lite` / `ws-plan-write` (companion generation, non-blocking), the consumer `config.json` (output language / enable switch), `bin/skill-dependencies.json` membership, and the catalog/FEATURES/docs + integrity surfaces. The generated `*-translated.md` is a consumer-owned run artifact under `{plansDir}/{slug}/`.

## Acceptance Criteria

- AC1: A packaged skill `ws-spec-translate-to-human` exists with `SKILL.md` (en-us body, valid frontmatter `name` / `description` / `version` / `invocation_names`), following the repository's skill-authoring conventions, and is registered in package membership.
- AC2: The skill writes a human companion `step-NN-{slug}.spec-translated.md` beside the source step artifact under `{plansDir}/{slug}/` (default `step-00-{slug}.spec-translated.md` for the spec step), and never overwrites the agent spec or the source artifact.
- AC3: The companion body has, in order, a short title and the sections `### Implementation`, `### UI Test`, and `### Out of scope` (the last omitted only when the source spec states no boundary); numbering is continuous within each section.
- AC4: Every acceptance criterion in the source spec maps to at least one implementation step or one UI-test step; each UI-test step is a single testable observation starting from an initial state and ending in a visible verification.
- AC5: Before writing, the skill gathers the listed context sources (agent spec, issue snapshot, original tracker item, MEMORY, changelog, README, docs, AGENTS/hub, optional vault) and records which were consulted; a blocking ambiguity is raised through `user-gate` when not in `autoMode`, otherwise recorded as an open question in the companion.
- AC6: The skill maps spec terms to the real system labels from project sources (for example a route provider or the screen templates) without expanding scope; when a screen/button name cannot be resolved, it is flagged rather than invented.
- AC7: The skill never implements product code and never edits the agent spec; it preserves the source ACs and Out-of-scope intent, and its only write target is the `*-translated.md` companion.
- AC8: Companion generation is wired into the refinement/planning path (`ws-spec-to-pr` / `ws-spec-to-pr-lite` / `ws-plan-write`) as a non-blocking, configurable step, and the output language is configurable (default `en-us`); enabling or disabling it does not change the agent spec or gate the pipeline.
- AC9: `npm run test`, `ws-check-harness` (Phases 0–5c), and `node test/test-harness-clean.js` exit clean; version bump + `npm run generate-integrity` + `verify-integrity` are consistent, and catalog/FEATURES/docs reflect the new skill.

### Design Intent

Greenfield skill, not a modification of existing behavior. There is no packaged human-translation skill and no `*-translated.md` convention in the harness, so there is no prior behavior to restore. Design intent is therefore limited to integration choices: where the companion lives, how it is named, and how the refinement step triggers it. The personal `traduzir-spec` skill in the issue is the reference format, not a harness dependency; the packaged skill re-expresses its rules in en-us and adds the context-gathering and refinement wiring the harness needs.

## Notes

- The companion is a run artifact under `{plansDir}/{slug}/`; it is consumer-owned and not a workflow gate input. It must never be read by downstream agent steps in place of the agent spec.
- The naming in the issue (`step-NN-{slug}.spec-translated.md`) is followed literally; a generalized `step-NN-{slug}.{artifact}-translated.md` is possible later but is out of scope here.
- Language: the packaged skill body is en-us (harness rule). The generated companion language is a consumer setting (default `en-us`, `pt-BR` supported) so the reference skill's pt-BR output remains achievable without shipping a pt-BR skill body.
- The reference skill's "map spec terms to the real system" rule is the reason AC6 requires project sources; it is what makes the runbook usable for manual QA rather than a restatement of the spec.
- `askQuestion` in the issue maps to the harness `user-gate`; `autoMode` records the open question instead of prompting (AC5).

## Out of Scope

| Feature | Reason |
|---------|--------|
| Implementing the translated steps as product code | The skill is a translation/runbook generator; implementation stays in the normal pipeline |
| Rewriting or replacing the agent `*.spec.md` | The agent spec remains the contract of record; the companion is additive |
| Translating plan/review/testing artifacts in this spec | The issue scopes the companion to the spec step; generalization is deferred |
| Automated browser execution of the UI-test steps | The companion is a manual runbook; execution tooling is a separate concern |
| A new SCM/provider intent | No remote surface participates in companion generation |
| Shipping a pt-BR skill body | Harness language rule keeps skill bodies en-us; only the generated output is configurable |
