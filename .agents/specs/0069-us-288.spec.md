# Specification — Align hub routing with unpackaged spec-memo companions (not vendor ws-memo)

## Description

Issue 288 is a **real hub/docs mismatch** in the published 0.4.2 workflows package, not consumer noise. It is **not** a request to ship `ws-memo` or `ws-session-tracking` from this repository.

Those two skill ids are authored by [spec-memo](https://github.com/jpolvora/spec-memo). This package ships `ws-spec-memo` as the harness bridge only. Root `AGENTS.md` already says runtime vault ops load `{globalSkillsRoot}/ws-memo` and must not vendor that tree. `bin/skill-dependencies.json` correctly omits both ids. `test-doc-sync.js` asserts root `CATALOG.md` only for skills that have a SoT `SKILL.md` under `.agents/skills/`.

The defect is that **shipped consumer hub docs contradict membership**:

- `ws-shared/autoload.md` Always-applied lists `ws-memo` and `ws-session-tracking` with `{skillsRoot}/…` paths. A workflows-only install has no those folders. Agents then try to `Read` missing `SKILL.md` at session start when a consumer root promotes Always-applied.
- `ws-shared/CATALOG.md` task router (and Start work) routes intents to those ids without an External/companion label. Layer tables correctly omit them (no disk SoT). Phase 4 triple-alignment (Layer ↔ disk ↔ router) then looks like a gap if the auditor treats router ids as packaged skills.
- `ws-check-harness` Phase 4 `phantom_routes[]` is **critical** for hub-referenced skills missing under the skills scan root, with Extra-package as the main exception. Task-router / Always-applied mentions of unpackaged companions are not Extra, so a consumer audit can report phantoms even when mechanical gates (duplicates, preamble, quoting, handoff) are green.
- Consumer `ws-shared/CATALOG.md` scope note links `[../../../bin/skill-dependencies.json](../../../bin/skill-dependencies.json)`. That path exists only at the **upstream** package root. After install, membership lives at `ws-shared/skill-dependencies.json`. Root `CATALOG.md` already uses `bin/skill-dependencies.json` (correct for this repo).

`installed-skills.json` omitting the two ids is **correct** when this installer never copied them. If spec-memo `install_skills` later places bodies under `{skillsRoot}`, they are a **foreign** tree: this installer must not prune them as unmanaged extras, and must not invent membership rows for skills it does not hash. Do not add the ids to `packages.workflows` solely so the installer tracks them.

Portable fix (agent- and IDE-neutral):

1. Declare `externalSkills` (or equivalent) in both `bin/skill-dependencies.json` and the shipped `ws-shared/skill-dependencies.json` copy for `ws-memo` and `ws-session-tracking` (source package spec-memo; not a `packages.*` member).
2. Move those ids out of Always-applied; document skip-when-absent (optional companion / `{globalSkillsRoot}`). Keep packaged `ws-spec-memo` as the in-tree bridge.
3. Mark CATALOG/task-router rows as external; do **not** add Layer 5 rows with `.agents/skills/ws-memo/SKILL.md` literals in this SoT.
4. Point the **consumer** CATALOG scope-note membership link at same-folder `skill-dependencies.json`.
5. Teach `ws-check-harness` Phase 2/4: declared external companions are **intentional omission**, not phantom/critical, when missing under the skills scan root (hybrid `{globalSkillsRoot}` still OK when present).

## Acceptance Criteria

- AC1: `packages.workflows.skills` and `packages.extra.skills` in `bin/skill-dependencies.json` and `.agents/skills/ws-shared/skill-dependencies.json` do **not** contain `ws-memo` or `ws-session-tracking`.
- AC2: Both skill-dependency files include an `externalSkills` array (or equivalent keyed list) whose entries include ids `ws-memo` and `ws-session-tracking` plus a portable note that they ship from spec-memo, not this package.
- AC3: `ws-shared/autoload.md` Always-applied table does not list `ws-memo` or `ws-session-tracking`. An **External companion skills** (or equivalent) section names both ids, `{globalSkillsRoot}` / optional `{skillsRoot}` resolution, and skip-when-absent (no session-start `Read` of a missing `SKILL.md`).
- AC4: `ws-configure-project/scripts/configure_autoload.py` `DEFAULT_ALWAYS_APPLIED` remains limited to packaged skills (no `ws-memo` / `ws-session-tracking`). Regenerated Always-applied output must not reintroduce those ids as mandatory.
- AC5: Root `CATALOG.md` and `ws-shared/CATALOG.md` task-router (and Start work, if present) rows for those ids state they are **external** (spec-memo / `{globalSkillsRoot}`), not Layer-table SoT paths. Neither catalog Layer table contains a `.agents/skills/ws-memo/SKILL.md` or `.agents/skills/ws-session-tracking/SKILL.md` literal.
- AC6: `ws-shared/CATALOG.md` membership scope note links `skill-dependencies.json` relative to `ws-shared/` (not `../../../bin/skill-dependencies.json`). Root `CATALOG.md` may keep `bin/skill-dependencies.json`.
- AC7: `ws-check-harness/PHASES.md` (and SKILL.md if it restates the exception) documents that hub/task-router/Always-applied references to `externalSkills` ids are **intentional omission** when the body is absent from the skills scan root; they must not be counted as `phantom_routes[]` critical. Presence under `{globalSkillsRoot}` remains OK (hybrid).
- AC8: A regression test fails if Always-applied packaged rows cite unpackaged ids, if consumer CATALOG membership uses `../../../bin/skill-dependencies.json`, or if Layer tables cite SoT literals for `externalSkills` ids.
- AC9: Installer `installed-skills.json` still does not list `ws-memo` / `ws-session-tracking` after a workflows-only install. Docs or installer comments state foreign trees installed by spec-memo are not this package’s membership and must not be pruned as managed extras solely because they are untracked.
- AC10: Shipped skill/hub/harness text added here uses portable vocabulary only (no host product names, no consumer project names). `npm run test` and the four Phase 5a mechanical gates exit 0.
