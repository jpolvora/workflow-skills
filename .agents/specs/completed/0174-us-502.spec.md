# Specification — Batch worker wedge: dispatched fix/review worker runs with zero output until interrupted

**State:** open
**Labels:** bug

## Description

A dispatched batch worker can run indefinitely with **zero observable output**: no round artifact, no telemetry event, no progress message, and no reply to a status ping. The parent can only interrupt the worker and redo the batch inline. This is one step worse than the documented loop-liveness case, which assumes a delivered worker result exists and only the follow-up turn failed.

The premature-turn guard already classifies a turn that **has ended**: `worker_turn_guard.cjs:85-104` returns `worker_zero_tool_calls` for an explicit zero tool-call count and `worker_missing_artifact` for unwritten required artifacts, and both exit 2 (`worker_turn_guard.cjs:167`). A worker that never returns emits neither signal, so the guard never runs. The parent-side watchdog signals are round-artifact freshness plus a `dispatch` telemetry event with no matching `finish` (`ws-goal-fix-pr/SKILL.md:69`), and with no first marker there is nothing to measure freshness against: "slow but working" and "wedged" are indistinguishable.

Observed shape (already sanitized in the issue): standard pipeline, Step 6 review batch; one fresh worker with a bounded brief (read diff, adversarial review, minimal fixes, write round report, return summary) per the fresh-worker-per-round-batch contract (`ws-goal-fix-pr/SKILL.md:120`) and the Step 6 review-fix round artifacts (`ws-code-review/SKILL.md:51`, `:97`); the worker stayed `running` across 4+ parent rounds with no file writes, no artifact and no summary; a status-check message was delivered with no reply; `interrupt` succeeded and the parent completed the identical batch inline in one round. No product-tree corruption resulted; the cost was rounds and attention.

Required behavior (the observable contract this spec pins):

- Every dispatched batch worker writes a **first liveness marker** within the effective worker liveness window after dispatch, giving the parent's freshness check a baseline.
- The marker is a run-runtime file, so it adds no workflow state write and cannot trip the post-exit revision accounting that derives its allowance from the turn's own op trace.
- The parent computes one deterministic verdict from three inputs: the recorded dispatch baseline, the marker, and any durable progress after dispatch — `pending` (window not elapsed), `alive` (marker present **or** durable progress), `wedged` (window elapsed, no marker, no progress), `no-baseline` (no dispatch record).
- Durable progress outranks marker absence: a marker-less worker that is demonstrably advancing stays `alive` and is never taken over. Only `wedged` authorizes takeover, and takeover never dispatches a second worker for a batch that is not proven wedged.
- The sanctioned no-output takeover is cancel-then-redispatch, or inline re-execution on the parent when re-dispatch is unavailable, recorded in the round artifact with measured ages.
- A status ping is never a sanctioned progress signal (the parent contract already forbids pinging a running worker turn, `WORKER-TURN-RULES.md:36-45`); when a ping is sent by any actor, its outcome is recorded as watchdog evidence instead of silence.
- The window resolves from configuration with a 600-second default, matching the observer's stall window (`ws-monitor/SKILL.md:64`).

Boundaries and touchpoints:

- Canonical dispatch contract: `.agents/skills/ws-spec-to-pr/WORKER-TURN-RULES.md` — single source of truth that dispatch builders quote rather than copy (`:3-6`).
- Deterministic evaluator: a Node helper sibling to `worker_turn_guard.cjs`, invoked with an explicit `node` launcher, printing a JSON record and using the same exit convention (0 for non-wedged, 2 for wedged).
- Run-runtime residue: `.runtime` names are allowlisted by `RUNTIME_NAMES` (`workflow_state.cjs:50-66`, which tolerates any `.md`) and validated by `validateRuntime` (`:2185-2189`, surfaced at `:2350-2351`), so the marker must stay inside that allowlist.
- Configuration surfaces: `config.schema.json` `defaults` block (`:114`) plus the example template (`config.json.example:126`) and the desktop editor (`Edit-WorkflowSkillsConfig.ps1`), which the harness change protocol requires to stay in sync.
- Watched owners: `ws-goal-fix-pr` § Loop liveness watchdog (`:65-71`), the Step 9 dispatch table (`STEP-DISPATCH.md:144`, `:168`), and the internal retry substeps (`STEP-DISPATCH.md:33`).
- Lite and inline-isolated postures carry no batch worker and therefore no marker obligation (`ws-goal-fix-pr/SKILL.md:121`, `:128`).

## Acceptance Criteria

- AC1: The dispatched batch worker shall write its liveness marker file within the effective worker liveness window after dispatch.
- AC2: When a batch worker starts, the worker shall write the marker under the run runtime directory as `worker-started-{step}-{batch}.md` with non-empty `step`, `batch`, and `dispatchedAt` fields.
- AC3: The marker write shall not increment the workflow state revision.
- AC4: While the liveness window has not elapsed since the recorded dispatch event, the evaluator shall report `pending`.
- AC5: When the liveness window has elapsed with no marker and no durable progress after dispatch, the evaluator shall report `wedged` and exit 2.
- AC6: When durable progress is recorded after the dispatch baseline, the evaluator shall report `alive`.
- AC7: If the telemetry stream holds no dispatch event for the evaluated step, then the evaluator shall report `no-baseline` and exit 0.
- AC8: When the parent receives a `wedged` verdict, the parent shall take over the batch without waiting for further rounds and record the takeover branch with measured ages in the round artifact.
- AC9: While the batch is not proven wedged, the parent shall not dispatch a replacement worker for the same batch.
- AC10: If a status ping is sent to a running batch worker, then the parent shall record the ping outcome as watchdog evidence instead of silence.
- AC11: The effective worker liveness window shall resolve from `defaults.workerLivenessWindowSec` and default to 600 seconds when the key is absent or invalid.
- AC12: Where the run executes inline or in the isolated fallback tier, the marker obligation shall not apply.
- AC13: The dispatch contract shall state the worker marker obligation, the parent watchdog contract, and the sanctioned no-output takeover branches in one canonical section.

## Original Issue Context

## Failure class

Batch-worker wedge: a dispatched round worker runs indefinitely with zero observable output. No round artifact appears, no status/progress is emitted, and a mid-run status message goes unanswered. The orchestrator can only interrupt the worker and redo the batch inline. This matches the documented Loop liveness watchdog pattern (worker result never arrives, no follow-up turn runs).

## Observed shape (sanitized)

- Standard pipeline, Step 6 review batch: one fresh worker dispatched with a bounded brief (read diff, adversarial review, minimal fixes, write round report, return summary).
- Worker stayed `running` across 4+ orchestrator rounds: no file writes under the assigned scope, no report artifact, no summary.
- A status-check message was delivered to the worker; no reply ever arrived.
- `interrupt` succeeded; the orchestrator then completed the identical batch inline in one round (review + 1 surgical fix + green suites + report).
- No product-tree corruption resulted; the wedge cost only rounds and attention.

## Why this matters for the contract

- The watchdog section covers "result delivered but no follow-up turn". This case is one step worse: **no result delivered at all**, so there is no batch output to take over from — only re-execution.
- A nudge (`send_message`-class ping) with no delivery confirmation or reply gives the orchestrator no signal to distinguish "slow but working" from "wedged".
- `dispatch` telemetry exists, but nothing requires a worker to emit a first liveness marker, so freshness checks have no baseline.

## Suggested hardening (non-blocking)

1. Require each batch worker to write a liveness marker (round artifact stub or telemetry `start` event) within N minutes of dispatch; missing marker = presumed wedge, eligible for resume-takeover without waiting for rounds to burn.
2. Confirm or fail status pings: if a mid-batch ping cannot be delivered/answered, surface that as watchdog evidence instead of silence.
3. Document the observed fallback explicitly: interrupt + inline re-execution of the batch (already practiced) as the sanctioned takeover when no batch output exists to resume from.

## Reproduction shape

1. Dispatch a review-sized batch worker (multi-file diff read + verification commands + report write) on a host where workers run detached.
2. Observe zero artifact/output across several orchestrator rounds while roster still reports `running`.
3. Interrupt; redo inline; compare effort.

### Design Intent

- **Intentional constraint:** the parent must never inject a message into a running worker turn — a mid-batch ping terminated a worker turn early (`WORKER-TURN-RULES.md:38-40`; `ws-goal-fix-pr/SKILL.md:71`). The hardening therefore adds a marker obligation and a read-only verdict; it must not reintroduce pinging as a progress probe.
- **Intentional constraint:** the harness keeps exactly one worker per slug/batch. A second worker for the same slug collides on the same state file and git branch (`.ws/memory/2026-10-10-host-declared-subagent-failure.md`, DO NOT), so the takeover branch is cancel-then-redispatch or inline, never a concurrent duplicate.
- **Intentional constraint:** every `update_state` operation bumps `revision`, and post-exit guards derive their allowance from the turn's own op trace rather than a fixed write count (`.ws/MEMORY.md` § `[2026-09-19] Post-exit tripwires must derive their allowance from the turn's own op trace`). A file marker keeps this accounting unchanged; a state-writing marker would add an unaccounted write.
- **Intentional constraint:** `.runtime` accepts only allowlisted residue names; any other name makes `update_state.cjs dispatch|finish` fail with `unknown .runtime residue` (`.ws/memory/2026-10-10-plan-runtime-residue-rejects-scratch.md`), so the marker name must be matched by `RUNTIME_NAMES`.
- **Intentional constraint:** new dispatch/fallback prose must mirror the existing posture carve-outs (lite-inline, Tier 1-3 ladder) and must not replace phrase-locked bullets that contract tests regex-lock (`.ws/MEMORY.md` § `[2026-09-18] Dispatch-contract prose must mirror posture carve-outs and keep test-locked phrasing`).
- **Accidental gap:** the guard was written to classify a completed turn's delivery quality, and the watchdog to recover a delivered-but-uncontinued loop; neither owns the case where a worker produces nothing at all, so no artifact, event, or timeout currently distinguishes a wedged worker from a slow one.

## Notes

- Evidence chain for the gap, in execution order: `STEP-DISPATCH.md:33` (internal retry substeps `reviewFix` / `fixPrPlan` / `fixPrExec` are re-dispatched workers) → `ws-goal-fix-pr/SKILL.md:120` (one fresh worker per round batch, bounded handoff, full output in the round artifact) → `ws-code-review/SKILL.md:51`, `:97` (round artifact `step-06-{slug}.review.r{n}.md` written only when the round reaches its report step) → `worker_turn_guard.cjs:85-104` (guard runs on a turn that ended) → `ws-goal-fix-pr/SKILL.md:69` (watchdog signals need a first marker to be meaningful) → `:71` (resume-takeover assumes a delivered result).
- Baseline that already exists: dispatch telemetry records `dispatchedAt` (`telemetry.schema.json:31`) and the append-only stream is written per dispatch (`STEP-DISPATCH.md:168`), so the parent already has a start timestamp; the missing half is the worker-side marker.
- Preferred shape of the fix (plan-level decision, not a product choice): one marker file per dispatch batch under `{us-dir}/.runtime/`, one deterministic evaluator with explicit verdicts and exit codes, one new `defaults` key resolved with a 600-second fallback, and contract prose added to `WORKER-TURN-RULES.md` plus the `ws-goal-fix-pr` watchdog section. Two halves are required: the marker alone still leaves the parent unable to act (no verdict), and a verdict alone still has no baseline without the marker.
- Marker payload correlation: the batch discriminator is the round number for round batches and the node id for DAG nodes, matching the existing dispatch vocabulary (`STEP-DISPATCH.md:144`); the evaluator correlates the marker to the latest `dispatch` event for the step, and a missing event yields `no-baseline` rather than a wedge.
- Persisted-failure lesson to preserve: a frozen state plus an unchanged `revision` is **not** proof of death — a worker can revive and advance hours later, and the stall window is time lost, not a product defect (`.ws/memory/2026-10-10-host-declared-subagent-failure.md`). AC6 encodes this by letting durable progress outrank marker absence, and the evaluator must fail open on unknown baselines.
- Observer alignment: `ws-monitor` already models `worker-session-stall` and `stalled-workflow` with a 600-second default window and a stopwatch (`ws-monitor/SKILL.md:64`, `:96-97`), and downgrades the stall finding to info while the state/telemetry clock advances. The workflow-side window default and the progress-outranks-absence rule keep the two views consistent.
- Configuration consequence: adding a `defaults` key requires the schema (`config.schema.json:114`), the example template (`config.json.example:126`), and the desktop editor (`Edit-WorkflowSkillsConfig.ps1`) to move together, verified by `node test/test-powershell-config-editor.js` (root hub § Config schema & GUI synchronization).
- Anonymization: the issue text carries no private consumer identifiers, and this spec adds none; the observed shape stays described by failure class.

## Out of Scope

| Feature | Reason |
|---------|--------|
| A hard kill or automatic timeout that terminates a worker without progress evidence | The reported defect is the missing baseline and verdict, not enforcement; an unconditional timeout would kill the live-but-slow sessions the liveness trap documents. |
| Mid-batch pinging as a liveness probe | Cancelled by the parent contract; a mid-batch ping terminated a worker turn early. AC10 only records the outcome when a ping happens anyway. |
| A new telemetry event type for the marker | The marker is a runtime file; adding a telemetry type would add a state write to a path whose revision accounting is deliberately trace-derived. The existing `dispatch`-without-`finish` anomaly remains the machine signal. |
| Changing `worker_turn_guard.cjs` verdicts or exit codes | Those cover ended turns and are phrase-locked by `test/test-worker-turn-guard.js`; this spec adds a separate evaluator instead of redefining them. |
| Applying the marker obligation to inline, lite, or Tier 3 isolated execution | Those postures have no dispatched worker and no parent/worker boundary to observe. |
| Extending `ws-monitor` findings or its transcript adapters | The observer side already reports stall classes for its own consumers; this spec owns the workflow-side baseline only. |

## Assumptions & Open Questions

| Assumption | Chosen default | Rationale | Confirmed |
|------------|----------------|-----------|-----------|
| Marker mechanism | A run-runtime file (`.runtime/worker-started-{step}-{batch}.md`) instead of a telemetry `start` event | The issue allows either; a file adds no state write (protecting trace-derived revision accounting) and stays inside the tolerated runtime residue names | n |

| Marker absence at the first poll | Report `pending` until the window elapses, never `wedged` | Fail-open on unknown state keeps resume and long-running workers safe; a wedge verdict must require elapsed time with no evidence | n |

## Validation & Observation Notes

### Telemetry & Observable Signals

- Evaluator verdict on a live run: `node {skillsRoot}/ws-spec-to-pr/scripts/worker_liveness_check.cjs --us-dir {us-dir} --step {N} --batch {id} --json` — prints one JSON record; exit 0 for `pending` / `alive` / `no-baseline`, exit 2 for `wedged`, exit 1 for usage errors.
- Marker presence during a batch: the marker file exists and is non-empty within the window after the step's `dispatch` event (`telemetry.jsonl`), and a state re-read shows the revision unchanged by the marker write.
- Durable progress probe: compare `telemetry.jsonl` and `.runtime/*` mtimes plus the state `revision` / `currentStep` / `completedSteps` against the dispatch baseline before acting on any suspected wedge.
- Round-artifact record of a takeover: the round artifact under `{reviewsDir}` (or the step report) names the takeover branch and the measured ages.
- Suite anchors: `node test/test-worker-turn-guard.js`, `node test/test-goal-fix-pr-orchestrator-dispatch.js`, `node test/test-ws-monitor-liveness.js`, `node test/test-liveness-checkpoints.js`, and the new evaluator suite in `test/test-suites.json`.
- Configuration gate: `node test/test-powershell-config-editor.js`, plus `npm run generate-integrity` / `npm run verify-integrity` once hashed skill content changes.

### Negative & Failing Test Scenarios

- Red test: dispatch a batch with a marker that is never written and freeze the state, telemetry, and runtime mtimes past the window; assert the evaluator reports `wedged` with exit 2. Before the change no evaluator exists and the parent burns rounds until it interrupts.
- Red test: keep the marker absent while advancing the state revision after dispatch; assert the evaluator reports `alive` and exit 0, proving marker absence alone never authorizes a takeover.
- Red test: remove every `dispatch` event for the step and assert `no-baseline` with exit 0 — an in-flight run resumed from an older state file must never be reported wedged.
- Red test: evaluate within the window with no marker and assert `pending` with exit 0 instead of a wedge verdict.
- Red test: write a marker whose name is outside the tolerated runtime residue names and assert `update_state.cjs finish` fails with `unknown .runtime residue`, pinning the naming rule the marker must satisfy.
- Red test: seed `defaults.workerLivenessWindowSec` with `0`, a negative value, or a string and assert the evaluator falls back to 600 seconds instead of wedging immediately.
- Red test: append a malformed line to `telemetry.jsonl` between valid dispatch records and assert the evaluator skips it and still resolves the correct baseline.
- Regression assertion: run the phrase-locked contract tests and assert the `worker_zero_tool_calls` / `worker_missing_artifact` signals, the `## Loop liveness watchdog` heading, and the observer liveness expectations still pass unchanged.
- Contract assertion: assert the canonical section states both the marker obligation and the no-output takeover branches, and that the lite / inline / Tier 3 exemption is present in the same section.
- Timing failure case: a batch whose marker lands after the window but before any verdict is acted on must report `alive`, so a slow-but-live worker is never cancelled by a race with its own first write.
