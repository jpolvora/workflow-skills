# Context — us-236 Prompt-to-spec-to-execution lifecycle

## Feature Boundary

This spec adds a **lightweight coordinator skill** for prompt-driven implementation in a consumer repo. It sequences existing skills (write-spec, spec-index, karpathy, senior-developer, changelog, self-learning) through three phases: intake, surgical implement+test, then canonical tracking updates.

It does **not** replace `ws-spec-to-pr` / `ws-spec-to-pr-lite` / `ws-multi-spec`. Those remain the only owners of `{plansDir}` FSM runs, `step-00` plan copies, DAG/interview, and ship/PR. This coordinator must not create plan trees.

It does **not** turn `ws-spec-index` into an intake orchestrator or `ws-sync-spec` into a multi-file tracking bus. Those skills keep their family roles (index checkboxes vs spec-body drift).

Consumer tracking docs named in the GitHub issue (`FEATURES.md`, `PLAN.md`, `PRODUCT.PRD`, `index.PRD`) are **consumer conventions** (spec-memo style). This upstream repo uses `FEATURES.md`, `CATALOG.md`, `CHANGELOG.md`, and `{specsDir}/index.PRD`. The skill defaults to the issue’s four-file list and must honor `tracking.canonicalFiles` when present.

## Implementation Decisions

1. **Architecture (chosen): Option A — new skill `ws-task-lifecycle`.** A dedicated coordinator keeps spec-family skills single-purpose and matches the issue title. Option B would overload `ws-spec-index` / `ws-sync-spec` past their router roles. Option C (Always-applied meta-skill) fights this package’s default `defaults.autoload: false` and the Always-applied overlap audit.
2. **Canonical tracking order (default):** `FEATURES.md` → `PLAN.md` → `PRODUCT.PRD` → `index.PRD` (plus matching slice spec checkbox/done log) → `ws-changelog` → `ws-self-learning`.
3. **Parameterization:** Optional `config.json` key `tracking.canonicalFiles` (array of repo-relative paths). Absent or empty → the default list above. Non-empty → Phase 3 walks that array in listed order, then still runs changelog and self-learning.
4. **Missing files:** Skip with an explicit skip note; do not abort later Phase 3 steps. Do not create stub `FEATURES.md` / `PLAN.md` / `PRODUCT.PRD` just to satisfy the list.
5. **Autoload default:** The new skill is **on-demand** (slash-invoke / task-router). The shipped `{sharedDir}/autoload.md` Always-applied table does **not** list it.
6. **Autoload opt-in:** `defaults.autoloadTaskLifecycle` (boolean, default false). `ws-configure-project --section autoload` asks whether to autoload `ws-task-lifecycle` like other Always-applied skills. Yes persists the flag and includes the skill on `--write-autoload`. Yes does not set `defaults.autoload` true by itself. This keeps prompt-driven work spec-driven when a consumer wants the same intake/track cycle as workflows.
7. **Index mark:** Use this repo’s legend: `[~]` in progress, `[x]` done (issue text wrote `[~]` / `[x]` equivalently).
8. **Tests:** Phase 2 runs `verification.backendTest` when configured; empty string → skip with a recorded reason (consumer may have no test alias).

## Deferred Ideas

- **Option B** (fold intake into `ws-spec-index` and tracking into `ws-sync-spec`) — revisit only if Option A glue proves too heavy.
- **Option C as shipped Always-applied default** — still out of scope. Consumer opt-in via `defaults.autoloadTaskLifecycle` is in this spec.
- **spec-memo off-repo memory adapter** — wait for Phase 2 harness adapters; this spec does not couple to an external vault.
- Auto-detect tracking files by glob instead of a default list + config override.
- Invoking `ws-sync-spec` as a mandatory Phase 3 step (optional later; body-drift sync is a different job than checkbox/done-log tracking).
