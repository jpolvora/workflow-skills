# Context — us-378: skill generator for the consumer project

Companion to `0110-us-378.spec.md`. Records the fit analysis the issue asked for: where a recurring consumer-specific skill generator belongs in this harness.

## Feature Boundary

The generator owns: the harvest protocol, the generated body lifecycle (seed blank, rewrite or append), the autoload row, the installer exclusion for the generated dir, the per-run summary, and the changelog entry.

It does not own: MEMORY.md and vault trap writes (`ws-self-learning` via `update-memory`), interactive per-correction capture (predecessor 0018 model), managed skill bodies, scheduling daemons, or git commit and push.

## Implementation Decisions

- **Option A, recommended: new shipped `ws-patterns-generator` plus consumer-owned generated `ws-project-patterns`.** The shipped skill holds the portable protocol; the generated body lives at project-local `{skillsRoot}/ws-project-patterns/SKILL.md` so it loads and autoloads as a skill. Reuses the 0018 conventions (consumer-owned storage, autoload row, configure seeding) in current-layout form: `runtime/` versus `templates/` split, `.cjs` helpers, project hub config. Fits the issue exactly: autoloaded, starts blank, improves on reruns, complementary to memory.
- **Option B, rejected: extend `ws-self-learning` with a skill-body projection.** Traps are anti-regression records with severity and frontmatter; projecting them into steering prose conflates two contracts. Self-learning stays the MEMORY owner; the generator reads MEMORY as one harvest source.
- **Option C, rejected: revive `ws-patterns-backend` / `ws-patterns-frontend` with a generator mode.** Layer-split interactive capture is a different interaction model, and those skills are absent from the current tree. The generator is cross-cutting harvest. Reuse the 0018 conventions, not its shape.
- **Option D, rejected: implement as a `ws-configure-project --section` only.** Configure runs once per project; the generator is recurring. Configure may offer the first seeding run, but the protocol lives in its own skill.
- **Seeding:** the generator first-run seeds the skeleton when the generated body is missing; `ws-configure-project` may offer that first run. Nothing seeds project claims.
- **Trigger:** manual invoke plus an orch post-close mention, never auto-run. Host schedulers may invoke the same command; configuring them is out of scope.
- **Storage path:** project-local `{skillsRoot}/ws-project-patterns/SKILL.md` (chosen) over `{sharedDir}/project-patterns.md` plus a shipped reader (rejected: extra indirection; a skill-shaped body autoloads directly).

## Deferred Ideas

- Host-scheduled recurring runs with run-history retention.
- Automated staleness scoring for rewrite decisions (runs stay agent-judged with summaries).
- Embeddings-based dedup and similarity across bullets.
- Cross-project pattern sharing protocol.
- Deep MCP introspection beyond configured names and notes.
- Automatic commit of regenerated bodies.
