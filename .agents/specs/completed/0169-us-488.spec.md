# Specification — fix(installer): use physical folder copy for Antigravity IDE on Windows and fix regex filter in skills.json

**State:** open

## Description

The installer exposes a secondary global target identified as `gemini`. It configures that host declaratively by upserting an entry into `<home>/.gemini/config/skills.json` and, historically, by sweeping any physical `ws-*` folders out of `<home>/.gemini/config/skills/`. Skills are also projected to secondary targets as directory junctions/symlinks (with copy fallback) by `projectSkillToTarget`.

This spec fixes a bug in that projection/configuration contract. On Windows, the target host's skill-discovery scanner does not follow ReparsePoints (directory junctions and symbolic links), and its slash-command UI indexes the physical tree only — it does not read virtual paths declared inside `skills.json`. As a result `ws-*` skills installed as junctions are invisible. In addition the declarative `include_only` filter is written as a shell glob `ws-*`, but the target interprets `include_only` entries as regular expressions; `ws-*` matches only `w`/`ws`/`wss`, never `ws-version`, `ws-doctor`, etc.

Technical boundaries and touchpoints:

- `bin/install-rules.js`: `getGeminiSkillsJsonPath`, `upsertGeminiSkillsJsonEntry` (defaults and call sites use `include_only: ['ws-*']`), `removeGeminiSkillsJsonEntry` (strips the literal `ws-*` pattern), `cleanupLegacyGeminiSkills` (sweeps physical `ws-*` folders).
- `bin/cli.js`: `projectSkillsToSecondaryTargets` (gemini branch upserts `include_only: ['ws-*']` then runs `cleanupLegacyGeminiSkills`), `removeSkillsFromSecondaryTargets` (gemini removal + legacy sweep), and one additional cleanup call site in the target-removal path.
- Tests that exercise the installer against a temporary home must not mutate the real user configuration at `<home>/.gemini/config/skills.json`.

The fix converts `gemini` target projection to real physical directory copies (Windows), stops the legacy sweep from deleting legitimate physical copies, corrects the `include_only` regex to `^ws-.*` in every upsert path, and isolates test configuration.

## Acceptance Criteria

- AC1: When the installer projects skills to the `gemini` target on Windows, the installer shall create each `ws-*` skill as a physical directory copy under `<home>/.gemini/config/skills/`.
- AC2: If a `ws-*` path under `<home>/.gemini/config/skills/` already exists as a junction or symbolic link, then the installer shall replace it with a physical directory copy.
- AC3: The installer shall write the `gemini` entry in `<home>/.gemini/config/skills.json` with `include_only` pattern `["^ws-.*"]` in every code path that upserts the entry.
- AC4: While the `gemini` target is installed, the installer shall keep physical `ws-*` directories under `<home>/.gemini/config/skills/` during install, update, and uninstall of other skills.
- AC5: When uninstall runs for the `gemini` target, the installer shall remove only the `ws-*` directories and the declarative `skills.json` entry it owns, leaving non-`ws-*` third-party skills intact.
- AC6: When the installer runs more than once, the installer shall keep exactly one `skills.json` entry per resolved skills path and shall not leave duplicate or dangling `ws-*` directories.
- AC7: The installer test suite shall isolate the `gemini` `skills.json` path so test runs never read or write the real `<home>/.gemini/config/skills.json`.

## Original Issue Context

## Summary
The global installer configures Google Gemini CLI / Antigravity IDE (`gemini` target) via declarative `~/.gemini/config/skills.json` (`upsertGeminiSkillsJsonEntry` in `bin/install-rules.js` and `bin/cli.js`). However, `ws-*` skills fail to appear in Antigravity IDE's slash command (`/`) autocomplete menu and agent runtime.

Investigation confirmed the root causes and the required architecture for Antigravity IDE support.

---

## Root Causes Identified

### 1. Antigravity IDE Directory Scanner Skips ReparsePoints (Junctions & Symlinks)
* On Windows, Antigravity IDE's internal filesystem scanner skips **ReparsePoints** (directory junctions and symbolic links) to avoid cycle loops.
* When skills are linked via junctions or symlinks (`Mode: l----`, `Attributes: Directory, ReparsePoint`), standard directory traversal (`os.ReadDir` / `fs.readdir` without `stat`) evaluates `isDirectory` as `false`.
* **Evidence:** All working skills in Antigravity IDE (e.g. `azure-devops`, `caveman`, `code-review`) are **real physical directories** (`Mode: d----`, `Attributes: Directory`). Replacing junctions with physical copies immediately restored discovery.

### 2. Slash Command (`/`) UI Autocomplete Does Not Scan `skills.json`
* Antigravity IDE's UI autocomplete for slash commands (`/ws-...`) in the chat prompt scans the physical directory tree:
  - Project level: `<workspace>/.agents/skills/`
  - Global level: `~/.gemini/config/skills/`
* It does **not** dynamically index virtual paths declared inside `skills.json`.
* When the installer previously introduced `cleanupLegacyGeminiSkills()`, it swept all physical `ws-*` folders from `~/.gemini/config/skills/`, causing all `/ws-*` commands to vanish from the UI.

### 3. Invalid Regex in `skills.json` (`include_only`)
* In `bin/install-rules.js` line 708 and `bin/cli.js` line 589:
  ```javascript
  upsertGeminiSkillsJsonEntry(homeDir, { path: entryPath, include_only: ['ws-*'] });
  ```
* Per Antigravity IDE specifications (`agy-customizations/docs/json_configs.md`), `include_only` takes **regular expression patterns**, not shell globs.
* In regex, `'ws-*'` matches `"w"` followed by zero or more `"s"` (`w`, `ws`, `wss`). It never matches `ws-version`, `ws-doctor`, etc. The correct regex pattern is `^ws-.*`.

### 4. Test Pollution in User Configuration
* Smoke tests write temporary directory entries (e.g. `C:\Users\...\AppData\Local\Temp\ws-targets-smoke`) directly into the permanent user configuration `~/.gemini/config/skills.json`.

---

## Solution & Implementation Plan for `workflow-skills`

### 1. Use Physical Directory Copies for the `gemini` Target
* For target `gemini`, copy skill directories as physical folders into `~/.gemini/config/skills/` using `simpleCopyDir` (or `projectSkillToTarget` with `symlink: false` on Windows).
* Remove or deprecate `cleanupLegacyGeminiSkills()`, which was destroying working folders.

### 2. Fix Declarative `skills.json` Filter
* If `skills.json` entry is maintained alongside physical copies, update the regex filter:
  ```javascript
  upsertGeminiSkillsJsonEntry(homeDir, { path: entryPath, include_only: ['^ws-.*'] });
  ```

### 3. Isolate Tests
* Mock or isolate `getGeminiSkillsJsonPath()` during tests so temporary test runs never alter the user's permanent `~/.gemini/config/skills.json`.

## Manual Workaround for Users

**Windows (PowerShell) — Copy physical folders:**
```powershell
# Remove any broken junctions/symlinks
Get-ChildItem "$HOME\.gemini\config\skills\ws-*" | Where-Object { $_.LinkType -or $_.Attributes -match "ReparsePoint" } | Remove-Item -Force -Recurse

# Copy real physical folders
Get-ChildItem "$HOME\.agents\skills\ws-*" -Directory | ForEach-Object {
    $dest = Join-Path "$HOME\.gemini\config\skills" $_.Name
    if (-not (Test-Path $dest)) {
        Copy-Item -Path $_.FullName -Destination $dest -Recurse
    }
}
```

*(After copying, reload the IDE via `Ctrl+Shift+P` -> `Developer: Reload Window` to re-index the slash command menu).*

### Design Intent

The declarative `skills.json` configuration and the symlink/junction projection strategy were deliberate choices from PR #335 and PR #269 (avoid per-skill folder projection and duplicate discovery; fall back to copy only when symlink creation throws). The `cleanupLegacyGeminiSkills` sweep was added to remove legacy junctions that duplicated declarative discovery. Those choices are intentional; what changed is newly discovered target-host behavior: its scanner does not follow ReparsePoints, and its slash-command UI indexes only the physical tree. The fix therefore narrows the projection strategy for the `gemini` target on Windows (physical copy) rather than reverting the declarative-config design.

## Notes

- The `gemini` target id is the stable installer identifier; host product naming is preserved only inside `## Original Issue Context` per the hub portability rule.
- `include_only` is a regular-expression filter for this target. Any future upsert/removal/merge logic that compares or strips `ws-*` must use the regex token `^ws-.*` consistently.
- `removeGeminiSkillsJsonEntry` currently strips the literal `ws-*`; it must recognize `^ws-.*` so uninstall still removes the entry it owns.
- Physical copies increase disk usage and require reinstall/update to refresh; this is accepted for discovery correctness.
- Deprecating `cleanupLegacyGeminiSkills` must not break the partial-uninstall legacy sweep requirement recorded in project memory — replacement behavior must still repair stale reparse points without deleting legitimate physical `ws-*` copies.
