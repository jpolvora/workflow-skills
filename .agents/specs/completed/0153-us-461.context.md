# Context — us-461 kanvas modal: show full spec content (Markdown rendered)

Companion to [`0153-us-461.spec.md`](0153-us-461.spec.md). Captures the product options considered when the tracker issue had only a title and an empty body.

## Problem

The `ws-kanvas` popup renders metadata only. Operators must leave the board and open the spec file on disk to read the requirement. The issue asks for a modal option to show the full spec content, Markdown rendered.

## Options

### O1 — New `/api/spec` endpoint + in-page Markdown renderer (chosen)

- Server: `GET /api/spec?slug={slug}` → `{ slug, path, markdown }`, path-confined to `{specsDir}`, typed errors.
- Client: popup toggle + a small dependency-free renderer (escaped HTML first).
- Pros: matches the existing `/api/card` query pattern; keeps `/api/card` lean; testable server-side; no new dependency.
- Cons: a hand-written renderer is a subset, not CommonMark.

### O2 — Extend `/api/card` with `?include=spec`

- Pros: one endpoint; fewer routes.
- Cons: makes the lightweight card payload optionally heavy; mixes the AC7 card contract with page content; harder to test independently.
- Rejected: separate concern deserves a separate read-only route.

### O3 — Return spec from `/api/board` for every card

- Pros: no extra round trip.
- Cons: bloats every board load with all spec bodies; the popup needs one card at a time.
- Rejected: wasteful and couples board refresh latency to spec size.

### O4 — Plain `<pre>` text, no Markdown formatting

- Pros: trivial, zero renderer risk.
- Cons: the issue title explicitly says "in .md rendered" — plain text does not satisfy it.
- Rejected: does not meet the ask.

### O5 — Vendor a full CommonMark/GFM library

- Pros: complete fidelity.
- Cons: violates the `ws-kanvas` "zero new `package.json` dependencies" rule and the self-contained/offline page rule.
- Rejected: dependency and portability cost outweigh subset limitations.

## Chosen direction

O1: a read-only `/api/spec` route plus a minimal, escaped Markdown subset renderer in `refs/board.html`. Scope is bounded to `refs/board.html`, `scripts/server.cjs` (and an optional `scripts/collect.cjs` read helper), plus tests.

## Residual risk

- Renderer subset may not cover exotic Markdown; acceptable for spec files (standard headings, AC lists, tables, code fences).
- Tables in specs render best as raw text if the subset omits table support; the spec's AC4 list intentionally excludes tables to avoid over-promising. Implementers may add table support if cheap, but it is not required.
