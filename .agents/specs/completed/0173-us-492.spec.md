# Specification — update: hub installed twice per run clobbers config.json.bak (backup ends up identical to live config)

## Description

The installer CLI (`bin/cli.js`, reached through `npx --yes github:jpolvora/workflow-skills …` or the `install-skills.sh` shim, which forwards the same argv) performs two phases per run: it copies the selected skill packages into the resolved skills root (`.agents/skills` project scope; `{globalSkillsRoot}` with `--global`), and then it ensures the shared hub (`ws-shared`) for the consumer. The hub phase (`ensureSharedHubInstalled`) refreshes managed hub content and calls `ensureSharedConsumerArtifacts` (`bin/cli.js:1375`), which upgrades the consumer config to the current shape and writes a pre-change snapshot to `config.json.bak` next to the live config (`bin/cli.js:983`, `999-1002`), then rewrites the live config from the packaged template plus the preserved consumer values (`bin/cli.js:1013-1016`).

The hub phase currently runs **twice in a single run** on an ordinary full `update`:

1. `afterSkillCopy('ws-self-learning', …)` (`bin/cli.js:1098-1106`) calls `ensureSharedHubInstalled(...)` from inside the update skill loop (`bin/cli.js:2714`). That in-loop call is intentional: installing `ws-self-learning` alone must seed the hub so memory works without selecting a workflow skill (comment at `bin/cli.js:1099-1100`).
2. `runUpdate` calls `ensureSharedHubInstalled('update')` again after the loop when `shouldEnsureHub(existingSkills)` is true (`bin/cli.js:2716-2719`). `shouldEnsureHub` (`bin/cli.js:823-829`) returns true when the selected set contains `ws-spec-to-pr`, `ws-spec-to-pr-lite`, or any id in `packages.workflows.skills` (`bin/skill-dependencies.json`), which is the normal full-update set.

The second call is not suppressed: `hubEnsured = true` is assigned **after** the second call, so the flag only guards the fallback refresh at `bin/cli.js:2723-2725`. The same shape exists in `runInstall` (`bin/cli.js:2059`, `2066`, `2072-2077`).

Root cause: because the hub is ensured twice, `ensureSharedConsumerArtifacts` writes the backup twice. Pass 1 backs up the original config and rewrites the live config to the upgraded shape; pass 2 backs up the **already-upgraded** config, so `config.json.bak` ends byte-identical to the live `config.json` and the pre-update snapshot is destroyed. If a real config migration ran, the only rollback artifact is gone.

Required behavior (the observable contract this spec pins):

- The hub install path runs at most once per `install` or `update` run, in project and global scope alike, and the run prints one hub status block (`bin/cli.js:1448`).
- `config.json.bak` keeps pre-change state: after a run that changes the live config bytes, the backup differs byte-for-byte from the live config.
- An existing backup that still differs from the live config is a usable rollback point and is preserved (not overwritten in place) across subsequent idempotent re-runs.
- Consumer-owned hub content is never lost or rewritten by the fix: config values, `STACK.md`, `MEMORY.md`/`memory/`, `CHANGELOG.md` (`hub-layout.json:60-69`).
- A run that does not change the config stays safe: it does not delete, truncate, or corrupt an existing backup and does not fail.
- Unusable inputs degrade safely: an unparseable live config is backed up from its raw bytes and left unmodified (`bin/cli.js:992-1002`, `1017-1019`), and a missing/unreadable `config.json.example` template leaves the live config unmodified (`bin/cli.js:1004-1011`, `1017-1019`).

Boundaries and touchpoints:

- Affected module: `bin/cli.js` — `afterSkillCopy`, `runInstall`, `runUpdate`, `shouldEnsureHub`, `ensureSharedHubInstalled`, `ensureSharedConsumerArtifacts`. `install-skills.sh` is a thin shim over the same Node CLI and needs no separate change.
- The backup path is derived from the resolved config location (`bin/cli.js:981-983`): the bootstrap config in project scope, the hub-joined config in global scope where `consumerHubDir() === managedHubDir()` (`bin/cli.js:155-158`). Project hub content resolves through the packaged hub resolver, so a configured `pathTokens.sharedDir` relocates the config and its backup together.
- Legacy hub relocation already preserves an existing backup: `relocateLegacyHub` moves `LEGACY_CONSUMER_HUB_NAMES` (which includes `config.json.bak`, `bin/cli.js:190-192`) only when the destination is absent (`bin/cli.js:960-963`).
- `config.json.bak` is classified `generatedLocal` / `ignore-by-default` (`hub-layout.json:71-81`) and is gitignored by the installed hub (`ws-shared/templates/hub.gitignore:16-17`); it is not consumer-owned tracked content.
- Existing test anchors: `test/test-install.js:866-879` (backup created on update, config preserved), `test/test-ws-shared-layout.js:286-289` (migration backup equals the original pre-update content), `test/run-tests.cjs:26-31` (suite must not overwrite a pre-existing `.ws/config.json.bak` in place).
- The desktop config editor keeps its own separate backup path (`Edit-WorkflowSkillsConfig.ps1:201`, asserted by `test/test-powershell-config-editor.js`) and is out of scope here.

## Acceptance Criteria

- AC1: The installer shall invoke the shared-hub install path at most once per `install` or `update` run.
- AC2: When the copied skill set contains `ws-self-learning` and at least one workflow skill that also requires the hub, the installer shall run one hub install and print a single hub status block.
- AC3: When an update run changes the bytes of the consumer `config.json` and no `config.json.bak` with differing bytes exists, the installer shall write the backup from the pre-change config bytes.
- AC4: If an update run changes the consumer config, then the installer shall leave `config.json.bak` differing byte-for-byte from the live `config.json`.
- AC5: While `config.json.bak` exists with bytes that differ from the live `config.json`, the installer shall preserve those backup bytes unchanged.
- AC6: When an update run leaves the consumer config bytes unchanged, the installer shall neither delete nor truncate an existing `config.json.bak`.
- AC7: If the existing consumer config is not valid JSON, then the installer shall back up its raw bytes without rewriting the live file.
- AC8: If an update run refreshes the shared hub, then the installer shall preserve consumer-owned hub files (config values, `STACK.md`, `MEMORY.md`/`memory/`, `CHANGELOG.md`) unchanged.
- AC9: Where the run targets the global install scope, the installer shall apply the same once-per-run hub install and backup-preservation guarantees.
- AC10: If the packaged `config.json.example` template cannot be read, then the installer shall leave the live consumer config unmodified.

## Original Issue Context

## Summary
`update` installs the `ws-shared` hub **twice** per run. Besides redundant work and duplicated console output, the second pass clobbers `config.json.bak`, so the "backup" ends up byte-identical to the live `config.json` and the pre-update config is **not** preserved.

## Environment
- workflow-skills **0.5.35** (`npx --yes github:jpolvora/workflow-skills`)
- Node `v22.22.2`, npm `10.9.7`
- Windows 11 (nvf4w node), Git Bash host shell
- Command: `npx --yes github:jpolvora/workflow-skills update --include-new --global`

## Observed
The hub block prints twice in a single update:

```
  Updating 'ws-self-learning'...
    Backed up .agents/skills/ws-shared/config.json → .agents/skills/ws-shared/config.json.bak
    Updated .agents/skills/ws-shared/config.json to latest format (preserved user values)
    Preserved existing ws-shared/STACK.md
    Refreshed stale ws-shared/autoload.md
  ws-shared/ hub updated (consumer config/MEMORY/stack/CHANGELOG preserved)
  ...
  Updating 'ws-write-a-skill'...
    Backed up .agents/skills/ws-shared/config.json → .agents/skills/ws-shared/config.json.bak
    Updated .agents/skills/ws-shared/config.json to latest format (preserved user values)
    Preserved existing ws-shared/STACK.md
    Refreshed stale ws-shared/autoload.md
  ws-shared/ hub updated (consumer config/MEMORY/stack/CHANGELOG preserved)
```

After the run:
```
SHA256(config.json)     = 32FA4934...50D
SHA256(config.json.bak) = 32FA4934...50D   # identical .bak
```

## Root cause
Two independent call sites run `ensureSharedHubInstalled('update')` in the same update:

1. `afterSkillCopy()` — `bin/cli.js:1098-1106` — fires when the copied skill is `ws-self-learning`:
```js
function afterSkillCopy(skillName, destPath) {
  if (skillName === 'ws-self-learning') {
    ensureSharedHubInstalled(hubPresent() ? 'update' : 'install');
  }
}
```
2. `runUpdate()` — `bin/cli.js:2716-2719` — fires again after the skill loop when `shouldEnsureHub(existingSkills)` (`bin/cli.js:823`) is true:
```js
if (shouldEnsureHub(existingSkills)) {
  ensureSharedHubInstalled('update');
  hubEnsured = true;          // only guards the fallback at 2723, NOT this call
}
```

Because `shouldEnsureHub()` is true for any normal full update (it returns true when `ws-spec-to-pr`, `ws-spec-to-pr-lite`, or any workflow skill is in the set), and `ws-self-learning` is always updated, the hub is installed twice on essentially every `update`.

The backup is written by `ensureSharedConsumerArtifacts()` — `bin/cli.js:999-1002` — *before* the config is rewritten at `bin/cli.js:1013-1016`:
```js
if (rawConfig) {
  fs.writeFileSync(configBakPath, rawConfig);      // bak <- current
  console.log(`    Backed up ${configDisplay} → ${configDisplay}.bak`);
}
...
const upgraded = upgradeConfigToLatestFormat(templateConfig, existingConfig);
fs.writeFileSync(configPath, `${JSON.stringify(upgraded, null, 2)}\n`);
```

- Pass 1: `config.json.bak` ← original; `config.json` ← upgraded.
- Pass 2: `config.json.bak` ← upgraded (original lost); `config.json` ← upgraded.

## Impact
- `config.json.bak` no longer represents the pre-update state (here it is byte-identical to `config.json`).
- If a real config migration occurs, the only snapshot of the original is destroyed on the second pass — no rollback.
- Redundant hub copy and duplicated `Updated/Backed up/hub updated` output makes the log misleading.

## Suggested fix
- Prevent the double invocation, e.g. set `hubEnsured = true` from the `afterSkillCopy('ws-self-learning')` path and skip the `shouldEnsureHub(...)` call when it is already set; or
- Make the backup write-once: only write `config.json.bak` when it does not already exist, so a genuine pre-update snapshot is retained across passes.

- Duplicate-risk note: existing assertions already encode the desired semantics (`test/test-ws-shared-layout.js:286-289` expects the backup to equal the original pre-update content; `test/run-tests.cjs:26-31` guards against in-place overwrite of a pre-existing `.ws/config.json.bak`), so the fix must not weaken them.

### Design Intent

- **Intentional constraint:** the in-loop hub ensure from `afterSkillCopy` exists so that installing/updating `ws-self-learning` alone seeds the hub and memory works without selecting a workflow skill (`bin/cli.js:1099-1100`). `git log -S "hubPresent() ? 'update' : 'install'" -- bin/cli.js` points at `29308d41` ("feat(us-351): relocate consumer hub to project .ws root"), which only retargeted that call to the relocated hub. Removing or unconditionally skipping the `ws-self-learning` path would break that contract.
- **Intentional constraint:** `config.json.bak` is a pre-migration snapshot by design — `git log -p -S "config.json.bak" -- bin/cli.js` resolves to `a8f19c53`, where the write sits immediately before `upgradeConfigToLatestFormat` rewrites the config, and `hub-layout.json` classifies the file as generated local content.
- **Intentional constraint:** the hub status line and the `Backed up …` line are user-facing progress output (`bin/cli.js:1001`, `1448`), so the fix reduces their count for a single run but does not rename them.
- **Accidental gap:** `hubEnsured` was introduced with `shouldEnsureHub` in `0e0bc9c2` ("feat(installer): promote shared skills to top-level installable packages") but is only read by the fallback branch (`bin/cli.js:2723`); it never suppresses the in-loop `afterSkillCopy` call, so a run can ensure the hub twice. The unconditional `fs.writeFileSync(configBakPath, rawConfig)` (`bin/cli.js:1000`) has no write-once or preserve guard, so the second pass destroys the first snapshot. No test or comment asserts that double installation is expected — the existing suite only ever exercised a single hub install per run.

## Notes

- Chain of evidence for the double call, in execution order: `bin/cli.js:2714` (update loop calls `afterSkillCopy`) → `bin/cli.js:1098-1106` (hub ensured for `ws-self-learning`) → `bin/cli.js:2716-2719` (`shouldEnsureHub` → hub ensured again, `hubEnsured` set afterwards) → `bin/cli.js:2723-2725` (fallback only). `runInstall` mirrors this at `bin/cli.js:2059`, `2066`, `2072-2077`.
- The backup write itself: `bin/cli.js:983` (path), `bin/cli.js:989-1002` (read + unconditional write), `bin/cli.js:1013-1016` (live config rewrite), `bin/cli.js:1017-1019` (preserve branch when no usable template/parse).
- Preferred shape of the fix (plan-level decision, not a product choice): make the hub ensure once-per-run (single guard covering both call sites, preserving the standalone `ws-self-learning` seed path) and make the backup write conditional so an existing backup that still differs from the live config is preserved. Both halves are required: the dedupe alone still overwrites a good backup on a later idempotent run, and a preserve-only guard alone would leave the duplicated log and redundant hub copy in place.
- `config.json.bak` is a generated local artifact, gitignored by the installed hub (`ws-shared/templates/hub.gitignore:16-17`) and classified `generatedLocal` in `hub-layout.json:71-81`; the fix must not change that classification or start tracking the file.
- Project and global scope diverge for the backup location (`bin/cli.js:155-158`, `981-983`): project scope uses the bootstrap config next to the hub, global scope uses the hub-joined config. Regression coverage should assert both.
- Stack invariant scan for the touched file is available as `node .agents/skills/ws-shared/runtime/scripts/scan_stack_invariants.cjs --stack typescript-node --file bin/cli.js` (currently reports 0 violations).

### Negative & Failing Test Scenarios

- Red test: seed an installed skill set containing `ws-self-learning` plus a workflow skill (for example `ws-spec-to-pr`) and run `update`; assert the stdout contains exactly one hub status block. Before the fix the block prints twice (`bin/cli.js:2714` then `2716-2719`).
- Red test: seed a pre-update `config.json` whose shape the current template upgrades, run `update` once, and assert `config.json.bak` equals the seeded bytes. Before the fix the second pass overwrites it with the upgraded bytes (`bin/cli.js:1000`), so the assertion fails.
- Red test: after one changing run, assert `hash(config.json.bak) != hash(config.json)`. Before the fix both hashes are identical, which is the exact symptom reported in the issue.
- Red test: with an existing `config.json.bak` that differs from the live config, run `update` twice and assert the backup bytes are unchanged after the second run (idempotent re-run must not destroy the rollback point).
- Red test: make the live `config.json` invalid JSON, run `update`, and assert the live file bytes are untouched while `config.json.bak` holds those same raw bytes and a parse warning is emitted (`bin/cli.js:992-1002`, `1017-1019`).
- Red test: remove or make unreadable the packaged `config.json.example`, run `update`, and assert the live config is left unmodified (`bin/cli.js:1004-1011`, `1017-1019`).
- Stack-invariant red test: configure a hub root that attempts directory traversal and assert the backup write stays contained or fails closed rather than writing outside the hub (`typescript-node.md` rule 4).
- Timing/robustness failure case: a run interrupted after the config rewrite but before the hub status line must not leave `config.json.bak` byte-identical to a partially upgraded live config.
