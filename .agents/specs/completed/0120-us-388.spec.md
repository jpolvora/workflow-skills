# Specification — ws-spec-multi standard workers do not persist {plansDir}/{slug} state, step artifacts, or telemetry

## Description

Standard child workers dispatched by `ws-spec-multi` can complete a full delivery — implementation, review-fix rounds, PR creation, and merge — while `{plansDir}/{slug}/` holds no workflow state, no step artifacts, and no telemetry. The batch then ships items whose child run is unobservable, unresumable, and carries no delivery-evidence artifact.

The omission is specific to workflow state rather than the whole pipeline: the same workers do follow other harness conventions (conventional `feat(#N): ...` product commits and `fix(#N): ...` review-fix commits). What is missing is the child's own `{workflow-id}.state.json` machine SoT plus its `.state.md` render, the per-step artifacts under `{plansDir}/{slug}/`, and `telemetry.jsonl`.

The blind spot is silent by construction. `ws-monitor`'s snapshot sets `expectedArtifacts: []` for `workflowType: ws-spec-multi` (`monitor_snapshot.cjs:1189`), while the same helper computes a real expected-artifact list for single-workflow pipelines (`:459`, consumed at `:511` and `:1227`). With an empty expectation set, an absent child plan/state/telemetry produces no finding — the monitor cannot see the missing state it was never told to expect.

Architecture touchpoints: the `ws-spec-multi` child-dispatch contract (`PROTOCOL.md` Phases 4, 4b, 5 — including the existing `child-workflow-id` cleanup reference at `:99`), the `ws-spec-to-pr` state/artifact contract that the child is supposed to honor, the `ws-monitor` expectation and finding model (`expectedArtifacts`, and the existing multi-spec finding family `multi-spec-idle` / `multi-spec-failed-item` / `multi-spec-concurrency` at `:581-600`), and the delivery-evidence consumer keyed on `step-08-*.result.md`.

## Acceptance Criteria

- AC1: A standard child dispatched by `ws-spec-multi` persists `{plansDir}/{slug}/{workflow-id}.state.json` (machine SoT, including `state.handoffs`) plus its `.state.md` render by the time the child reaches close.
- AC2: The child writes the step artifacts for the steps it actually ran, under their contract names (`step-01-{slug}.plan.md`, and the other step files the pipeline executed) — never an ad-hoc name such as `plan.md`.
- AC3: The child writes `{plansDir}/{slug}/telemetry.jsonl`.
- AC4: `PROTOCOL.md` states the required child artifact set and the workflow id used for child state, so the batch orchestrator and the dispatched worker agree on the same `{plansDir}/{slug}` path.
- AC5: A child that reaches worker exit without the required state file or `step-01` artifact for the active item fails closed with a surfaced reason, mirroring the existing `missing-artifact` class, instead of being recorded `shipped`.
- AC6: `ws-monitor` emits a `missing-child-state` finding when a multi-spec item advances without child state, so the blind spot is surfaced instead of silent.
- AC7: A completed child leaves `{plansDir}/{slug}/step-08-*.result.md` so delivery-evidence consumers (for example `ws-spec-index sync`) have a key to read.
- AC8: The batch report does not claim delivery evidence for an item that lacks child state.
- AC9: `npm run test`, `ws-check-harness`, and `node test/test-harness-clean.js` exit clean, and a multi-spec fixture covers the `missing-child-state` finding.

## Original Issue Context

`ws-spec-multi` standard child workers can complete full delivery (implementation, review-fix rounds, PR creation, and merge) while `{plansDir}/{slug}/` contains **no workflow state, no step artifacts, and no telemetry**. The batch therefore ships items whose child run is unobservable, unresumable, and has no delivery-evidence artifact.

Reproduced on two consecutive items in one standard batch run (5 items, `flowMode: standard`):

1. **Item A — completed and shipped (PR merged).** `{plansDir}/{slug}/` contained only the pre-existing `step-00-<slug>.spec.md` and `step-00-<slug>.issue.json`. No `*.state.json` / `.state.md`, no `step-01-*.plan.md`, no `step-02` / `step-03` / `step-05` / `step-06` / `step-07` / `step-08` artifacts, and no `telemetry.jsonl`. Product files were committed and the PR merged.
2. **Item B — in progress.** `{plansDir}/{slug}/` contained a bare `plan.md` (not the contract name `step-01-<slug>.plan.md`) plus the two `step-00` files. Still no state and no telemetry.

The child workers do follow other harness conventions (conventional `feat(#N): ...` product commit and `fix(#N): fix issues from review threads [...]` review-fix commit), so the omission is specific to workflow state/artifacts rather than the whole pipeline.

Expected, per `ws-spec-multi/PROTOCOL.md` Phase 4-5: each standard item dispatches `ws-spec-to-pr` and is afterwards referred to as a `child-workflow-id` with child-orch Phase A cleanup. `ws-spec-to-pr` mandates a `{workflow-id}.state.json` (machine SoT) plus `state.handoffs`, and per-step artifacts under `{plansDir}/{slug}/`. A completed standard child should leave the state file and its `.state.md` render, `step-01-{slug}.plan.md` plus the other step artifacts the pipeline ran, and `telemetry.jsonl`.

Impact reported:

- `ws-monitor` cannot observe the child run. For a multi-spec workflow the snapshot reports `expectedArtifacts: []`, so the absent child plan/state/telemetry produce **no finding**; the blind spot is silent.
- No resumable state: a child interrupted mid-run has nothing to resume from.
- No `step-08-*.result.md`, so delivery-evidence consumers (for example `ws-spec-index sync` and index/Done-log bookkeeping) have nothing to key on.

Suggested fix: make the child-dispatch path create, and the worker honor, the standard `{plansDir}/{slug}` state and step artifacts; or fail closed at worker exit when `{plansDir}/{slug}` has no state file / `step-01` for the active item, mirroring the existing `missing-artifact` class; and add a monitor finding (for example `missing-child-state`) so a multi-spec item that advances without child state is surfaced instead of silent.

Secondary observations from the same run:

- The batch state header `updatedAt` did not advance with the row updates (header stayed at run-creation time while row `updatedAt` moved forward).
- Three unrelated tracked files under `{specsDir}` (`step-00-<slug>.classify.md`) were left deleted and uncommitted across items, unrelated to the active slug.

### Design Intent

Modification, not greenfield. The child pipeline already defines the state and artifact contract, and `PROTOCOL.md` already names a `child-workflow-id` for Phase A cleanup — so the missing piece is that the dispatch/exit path neither requires nor verifies child persistence.

Two complementary hardening points:

1. **Contract and enforcement** — state the required child artifact set in the dispatch contract and fail closed at child exit when it is absent, reusing the existing `missing-artifact` finding class rather than inventing a parallel mechanism.
2. **Observation** — extend the monitor's multi-spec expectation model so an item that advances without child state produces a finding. The monitor's own code shows the intended shape: `expectedArtifacts()` exists and is consumed for single workflows, while the multi-spec branch returns `[]`; the fix is to populate expectations for multi-spec items from the batch queue rather than to add a separate detector.

Ownership of the writer (child orch creates the state at dispatch time versus the worker creating it at its own step 0) is an open question recorded below; both satisfy AC1, and the choice affects only which component is authoritative.

## Notes

- The blind spot is structural: `monitor_snapshot.cjs:1189` returns an empty expectation list for multi-spec, so absence of child artifacts cannot produce a finding no matter how long the run is observed.
- A bare `plan.md` (Item B) shows the worker is writing artifacts at the right directory but with a non-contract name; AC2 targets that drift separately from AC1's missing state.
- `step-00-*.issue.json` snapshots are audit-only and were correctly present, which confirms the child does write into `{plansDir}/{slug}/` — it just omits the state, step, and telemetry surfaces.
- The batch header `updatedAt` symptom is the same defect class tracked separately by #393 AC6; this spec does not duplicate it.
- Reproduction: any standard multi-spec batch; inspect `{plansDir}/{slug}/` after a child merges.
