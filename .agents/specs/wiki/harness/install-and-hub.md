# Install & Hub (`harness`)

> Provenance: `bin/cli.js`, `bin/skill-dependencies.json`, `.agents/skills/ws-shared/runtime/hub-layout.json`, root `AGENTS.md` § Skill SoT, living synthesis of specs 0002, 0007, 0010, 0013, 0017, 0027, 0032, 0037, 0042, 0052, 0058, 0061, 0066, 0069, 0070, 0071, 0083, 0100-us-351, 0106, 0115-configurable-hub-root, 0119-us-389.

## Feature

The harness ships portable skill bodies through a package installer that supports Workflows-only and Full package selections, project-local installs, and optional global installs under `$HOME/.agents/skills`. Canonical skill content lives only under `.agents/skills/ws-*` in the upstream source tree; consumers receive managed copies on install and update. Hybrid execution resolves skill bodies local-first then `{globalSkillsRoot}`, while project `$PWD/.ws/config.json` always overrides global hub defaults. The consumer hub splits into installer-owned `runtime/` (contracts, scripts, schemas), setup-only `templates/` (seeds), and consumer-owned root files (`config.json`, `STACK.md`, `MEMORY.md`, `CHANGELOG.md`), classified by `hub-layout.json`. Upstream authoring prose in root `AGENTS.md` stays separate from the consumer-portable hub contract in `.ws/AGENTS.md`. Secondary global host targets stay minimal: Claude Code (`~/.claude/skills`) and OpenAI Codex (`~/.codex/skills`) receive per-skill folder projections, while Gemini CLI and Antigravity IDE are configured declaratively through `~/.gemini/config/skills.json`, where the installer upserts one entry pointing at `~/.agents/skills` with `include_only: ["ws-*"]` instead of creating dozens of junctions or copies.

## How it works

Authors hash and publish only from `.agents/skills/` in the upstream package. Skill bodies never name host products, never hardcode consumer artifact paths, and never ship legacy-path shims; install and update deliver the latest layout only. Config resolution follows explicit override, then project-local hub, then global fallback. Global installs write only the minimal consumer bundle and never copy `runtime/`, `templates/`, manifests, or memory files into the global tree as consumer data.

Package selection auto-selects transitive dependencies when a skill is chosen, and deselect never silently drops dependents. Retired skill ids migrate idempotently to canonical ids during update. Unpackaged external companions such as `ws-memo` and `ws-session-tracking` appear in `externalSkills`, are never vendored, and are never required for core workflow installs. Consumer mode audits `ws-shared/AGENTS.md` as the hub entrypoint; no skill or installer may require a repo-root `.agents/AGENTS.md`. The `rules.harness` path resolves through a thin local pointer or documented global fallback.

The Gemini entry upsert is idempotent and non-destructive: unrelated `entries` and `inherits` blocks survive; a matching unrestricted entry (no `include_only`) is never narrowed; and when a filtered entry already exists the `ws-*` pattern is appended rather than duplicated. A malformed or wrongly shaped `skills.json` is backed up to `<file>.bak.<timestamp>` and reinitialized to a safe structure. Legacy `ws-*` and `ws-shared` junctions, symlinks, and directories under `~/.gemini/config/skills/` are swept on configuration so declarative discovery cannot duplicate folder projections, while non-workflow skills stay untouched. Global uninstall removes only the wildcard pattern from the managed entry, drops the entry entirely when no wildcard paths remain and no `ws-*` skills stay installed, and a partial uninstall still sweeps legacy junctions while preserving the entry.

Secondary targets are auto-detected with read-only probes: an existing host root directory (for example `~/.gemini` from Antigravity), the target skills directory, or the target config file counts as consent, while regular files at a host root never do. Auto-detected targets are best-effort, so a failing projection warns and continues instead of aborting the explicitly requested canonical install, and a bare `update --global` re-detects them so previously unrecorded targets heal. Projection clears broken reparse points first: `projectSkillToTarget` uses lexical existence checks so dangling Windows junctions or symlinks are removed before symlink creation or copy fallback, avoiding `EEXIST` and `ENOENT` failures across install and update.

Interactive global install and update always present the host-target picker (canonical plus `claude`, `codex`, and `gemini`) with recorded and auto-detected targets pre-selected, so pressing Enter keeps the current set. Non-interactive runs (piped stdin or `--yes`, with `update` gaining `--yes`) skip the prompt and reuse recorded targets before auto-detecting pre-existing host directories. An explicit `--targets` value, even `canonical` alone, skips both the prompt and auto-detection for that run. Copy-versus-symlink default follows the mode recorded in `installed-skills.json`, keeping repeat runs consistent with the first install choice.

Naming law requires every id containing `spec` to match `^ws-spec-`, with identical strings across folder name, `name:` frontmatter, dependency graph keys, and router rows. Subagent projection via `compile_host_subagents.cjs` is disabled by default, compiled agents set `disable-model-invocation: true`, and unsupported hosts fall back to generic dispatch.

Node 22 is the only runtime any shipped skill, installer entry, or `package.json` script may depend on. Every packaged Python helper was rewritten as CommonJS `.cjs` (which `require()` shared helpers regardless of the root `"type": "module"`) or deleted, provider intents kept their names while only the launched file changed, and recipes invoke skill helpers with an explicit `node` launcher while `bash` survives only for thin host adapters that locate Node and `exec` a `.cjs`. Consumers install and run the package with Node 22 and nothing else. The authoring contract in root `AGENTS.md` and `SKILL_AUTHORING.md` forbids new `.py` files, and `ws-check-harness` reports critical when any `.py` appears under `.agents/skills/` or `bin/`, so the second runtime cannot drift back in.

The upstream authoring hub and the consumer hub are semantically separated and mechanically enforced. Repo-root `AGENTS.md` owns the Skill SoT, the dogfood session contract, the global-vs-local invoke tie-break, and the maintainer ship checklist, while `{skillsRoot}/ws-shared/runtime/AGENTS.md` (global fallback `{globalSkillsRoot}/ws-shared/runtime/AGENTS.md`; thin entrypoint `{sharedDir}/AGENTS.md`) carries only consumer-portable obligations behind an explicit consumer-hub identity banner. `{skillsRoot}/ws-shared/runtime/CATALOG.md` keeps the consumer task router and the external-dependencies mirror and carries no upstream maintainer tables. The installer copies the managed `ws-shared/` tree (runtime + templates) into the skills install only; the consumer hub (`.ws/`) holds consumer-owned config, the generated entrypoint, and installer metadata, never `runtime/` or `templates/`. `ws-check-harness` fails the upstream audit when the consumer hub contains any denylisted upstream-only phrase, and the context-budget gate caps `{skillsRoot}/ws-shared/runtime/AGENTS.md` at 14,000 bytes, so size pressure and content rules together keep the two hubs from reconflating.

The consumer shared-data folder lives at `{projectRoot}/.ws` with the same tree the previous skills-tree location held: consumer-owned `config.json`, `STACK.md`, and memory/changelog files beside installer-owned `runtime/` and setup-only `templates/`, classified by `runtime/hub-layout.json`. The folder is committable by default and never git-ignored by the installer. Path resolution is token-strict everywhere: `{skillsRoot}` expands as explicit override, then project `.agents/skills`, then `{globalSkillsRoot}`; `{sharedDir}` is always the project `.ws`, whose `config.json` wins over any global hub config; consumer-facing prose and scripts always resolve hub and skill-tree locations through `{sharedDir}` / `{skillsRoot}` tokens instead of hardcoded paths, and bare `ws-shared/` shorthand is banned from link targets. A config-dependent skill invoked globally without a project hub fails closed with a pointer to `ws-configure-project` instead of silently reading global config as project config.

The shared hub root is relocatable through one resolver instead of scattered path logic. A single module under `{skillsRoot}/ws-shared/runtime/scripts/` derives the hub root from bootstrap discovery of `<repo>/.ws/config.json`, then the configured `pathTokens.sharedDir`, then the `.ws` default, and the installer, the autoload configurator, the skill seeder, and the hub-layout reads all call it. Install, update, uninstall, and migration therefore write hub artifacts (ignore rules, entrypoint pointer, generated autoload rows, manifests, `STACK.md`) under the configured root with integrity records kept consistent, while generated autoload rows and link prefixes render against the same root so the renderer never reverts them.

The test suite stays side-effect free against the live hub. Every editor invocation from tests passes an explicit isolated `-ConfigPath` pointing at a temp copy, diagnostic-only runs perform no writes and leave no `.bak` behind, PowerShell path literals are quoted so suite failures clean their fixtures, and the hub-mutation guard hashes backup content and runs on the failure path as well as the happy path so a green run never flips delivery-artifact flags in the repository's own `.ws/config.json`.

## Backend

The installer entrypoint is `bin/cli.js` with flags such as `--global`, `--targets`, and `--symlink`. `bin/skill-dependencies.json` carries the install graph, `packageVersion`, and `externalSkills`. `bin/install-rules.js` implements the target registry and `HUB_WHITELIST`. `retired_artifacts.cjs` tracks `RETIRED_HUB_FILES` and `RETIRED_DEFAULTS_KEYS`. Multi-host global installs keep `$HOME/.agents/skills` canonical and project per-skill junctions on Windows or symlinks on POSIX into companion host skill directories without clobbering third-party skills. Gemini declarative configuration runs through `getGeminiSkillsJsonPath`, `readGeminiSkillsJson`, `upsertGeminiSkillsJsonEntry`, `removeGeminiSkillsJsonEntry`, and `cleanupLegacyGeminiSkills` in `bin/install-rules.js`; `GLOBAL_HOST_TARGETS` carries the `configSubpath` for the gemini target and `detectExistingSecondaryTargets` drives the consent probes. The shared `promptSecondaryGlobalTargets` picker with the `computeTargetPreselectIds` helper serves both install and update, and the CLI help documents the prompt, `--targets`, and `--yes` behavior. `test/test-install.js` covers skills.json creation, idempotency, legacy cleanup, custom-entry preservation, corrupt-JSON recovery, and uninstall.

Consumer configuration uses `pathTokens` (`skillsRoot`, `sharedDir`), `providers.active` and `providers.scm`, `plans.specsDir` and optional `plans.wikiDir`, `rules.*` guardrail paths, and `defaults.specializedSubagents`. Consumer-owned scripts resolve the hub from `$PWD` via `resolve_consumer_root.cjs`, never from `__file__` inside a managed skill copy. Hub-root resolution is single-sourced through `resolve_hub_root.cjs`, with `bootstrap_runtime.cjs` and `cli_spawn.cjs` sharing the same bootstrap so installer, configurator, and generator agree on one root, and `resolve_proof_of_work.cjs` wires the optional evidence step through the same contract.
