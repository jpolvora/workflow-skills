# Specification — ws-spec-multi appends a duplicate queue row for an item, causing double processing

## Description

`ws-spec-multi` can append a duplicate row to its run-state queue instead of transitioning the existing row for that spec. The run state then holds two rows for one slug — one `in_progress` (or `shipped`) and one stale `pending` — and the reported item count grows past the original selection length.

Because the Phase 3 selection rule picks the next `pending` / `in_progress` row, a duplicate row is not cosmetic: it is selectable work. The immediate effect is wrong run metrics and duplicate row keys; the durable effect is a resume hazard, because the resume policy restarts at the first `pending` item, so re-running the state file re-dispatches specs that already shipped.

Architecture touchpoints: the `ws-spec-multi` state contract (`STATE.md` queue schema and Resume Policy), the phase instructions that write and mutate the queue (`SKILL.md`, `PROTOCOL.md`), and the multi-spec eval fixture (`ws-spec-multi/evals/evals.json`). No config-schema, GUI, or provider surface is involved.

## Acceptance Criteria

- AC1: Queue mutations are keyed by spec identity (`specPath` or `slug`); transitioning an item to `in_progress` / `shipped` / `skipped` / `failed` updates that row in place and never appends a second row for the same spec.
- AC2: A state write that would emit a duplicate row index or duplicate `slug` fails closed and surfaces the conflict instead of writing the file.
- AC3: The reported item count equals the length of the Phase 2 selection and stays constant while items ship.
- AC4: After a completed standard batch, the state table holds exactly one row per selected spec, and every row is terminal (`shipped`, `skipped`, or `failed`).
- AC5: Resuming a `completed` state file re-dispatches zero already-`shipped` items (no phantom `pending` rows survive close).
- AC6: The per-row `updatedAt` advances on each transition, and the run frontmatter `updatedAt` advances on every state write.
- AC7: `STATE.md` documents the one-row-per-spec invariant and the fail-closed duplicate guard in the queue schema and Resume Policy.
- AC8: `ws-spec-multi/evals/evals.json` covers the duplicate-row scenario, and `npm run test` plus `ws-check-harness` exit clean after the change.

## Original Issue Context

`ws-spec-multi` can append a **duplicate queue row** for an item instead of updating the existing row. The run state then contains two rows for the same slug, one `in_progress` and one `pending`, and the reported item count grows past the original queue length. Because Phase 3 selects the next `pending`/`in_progress` row, the duplicated slug is worked twice.

Observed on a single standard batch run with an initial queue of 5 items. After item 3 shipped, the run state contained 6 rows:

```text
| # | slug                   | specPath                              | flowMode | status      | ... |
| 1 | us-381                 | .agents/specs/0112-us-381.spec.md     | standard | shipped     | ... |
| 2 | us-380                 | .agents/specs/0113-us-380.spec.md     | standard | shipped     | ... |
| 3 | configurable-hub-root  | .agents/specs/0115-configurable-hub-root.spec.md | standard | shipped | ... |
| 4 | us-385                 | .agents/specs/0116-us-385.spec.md     | standard | in_progress | ... |
| 4 | us-385                 | .agents/specs/0116-us-385.spec.md     | standard | pending     | ... |
| 5 | us-386                 | .agents/specs/0117-us-386.spec.md     | standard | pending     | ... |
```

- Duplicate row index: `4` appears twice.
- Duplicate slug: `us-385` appears as both `in_progress` and `pending`.
- Reported counts changed mid-run: `shipped=3/5` became `shipped=3/6` as the new row appeared.
- The pre-existing row's `updatedAt` stayed at run-creation time while the new `in_progress` row carried the current timestamp.

Final outcome of the same run: it reached `status: completed` with all 5 originally selected items shipped and merged, reporting `5/7` shipped and leaving two phantom rows:

```text
| 4 | us-385 | ... | standard | pending | | | | 2026-09-22T02:28:01Z |
| 5 | us-386 | ... | standard | pending | | | | 2026-09-22T02:28:01Z |
```

Both phantom rows carry `updatedAt` equal to run-creation time and duplicate slugs already marked `shipped` in the same table.

Expected: one queue row per selected item, keyed by spec path or slug. Transitioning an item from `pending` to `in_progress` must update the existing row rather than append a new one, and the item count must stay at the selected queue length.

Suggested fix: key queue mutations by `specPath`/slug and update in place; add an idempotency assertion that raises on duplicate index or slug; freeze or recompute the item count from the Phase 2 selection.

### Design Intent

Modification, not greenfield: the run-state schema and phase transitions already exist and were exercised by the reporting run. The change hardens the existing mutation path — one-row-per-spec keying plus a fail-closed duplicate guard — and adds the invariant to the documented contract. Introducing a separate state store or a script-owned writer is explicitly deferred; the minimal fix keeps the current Markdown state file and the current writer.

## Notes

- Two symptoms share one root cause candidate: rows are appended when the state is written, and the original scan row is left untouched instead of being consumed by the transition.
- The duplicate is observable in two ways — a repeated row index and a repeated slug — so the guard should check both.
- The frontmatter `updatedAt` did not advance across the whole run (`createdAt` equals `updatedAt` in the final file), which weakens the state file as a liveness signal.
- Existing number collisions in `{specsDir}` (`0099`, `0100` each appear twice) show the same append-without-keying class of defect in a sibling writer; the fix here should not be scoped to that unless the shared helper is the actual root cause.
