# Context — us-386 optional step proof-of-work

Companion to [`0117-us-386.spec.md`](0117-us-386.spec.md). Records the gray areas that carry two or more valid product options. Not a plan artifact.

## Feature Boundary

The feature is a single opt-in post-completion step plus its configuration surface. It starts after the workflow is finished and never participates in planning, implementation, review, or shipping.

In boundary:

- Two boolean switches and one output-path setting in `config.json`.
- One `user-gate` after close on both workflows (standard after Step 8 / Step 9 convergence; lite after Step 4).
- Invocation of an evidence-collector skill that writes numbered screenshots plus `EVIDENCE.md` under the configured folder.
- Schema, example config, PowerShell GUI, and hub documentation updates.

Out of boundary: evidence auto-commit, new browser capabilities, PDF or dashboard rendering, timesheet capture, and any change to PR creation or the goal-fix-pr loop.

## Implementation Decisions

### Decision 1 — Evidence-collector ownership (OPEN)

Two valid options:

1. **Package a first-party skill** in this repository (for example `ws-proof-of-work`) and copy the issue's example body into the shipped skill set. Consistent naming with existing `ws-*` skills, single source of truth, installer-managed.
2. **Config-wire an external skill.** Ship only the switch, the gate, and the invocation contract; resolve the collector by skill id (for example a consumer-installed `proof-of-work`). Keeps the package free of browser automation and lets consumers supply their own collector.

Trade-off: option 1 increases package surface and must satisfy portability and harness rules (no host product coupling, Node-only scripts); option 2 keeps the package lean but adds a soft external dependency that must fail closed with a clear skip reason.

Recommended default pending confirmation: **option 2 (config-wire)** for this spec, because the gate, keys, and fail-closed skip reason are independently valuable and the collector body is environment specific. Packaging a first-party collector would be a follow-up spec.

### Decision 2 — Config key placement

The issue names flat keys (`config.enableOptionalProofOfWork`). This repository groups switches under sections (`defaults.*`, `plans.*`, `preview.*`). Keep the proposed key names but place them under `defaults.*`, and keep the output path with them. Any schema or GUI change must stay in sync (`node test/test-powershell-config-editor.js`).

### Decision 3 — Gate placement

The step belongs after close on both workflows. Placing it inside `ws-ship-pr` was rejected: shipping can be skipped (push-only or skip), while the issue asks for the offer after the workflow is done. The orchestrator owns the post-close transition and stays the single place that presents the gate.

### Decision 4 — Failure semantics

When the collector is unavailable or the host lacks browser capability, the step records a skip with a reason and never fabricates evidence. This mirrors the existing optional-step convention in the orchestrators.

## Deferred Ideas

- First-party packaging of a portable evidence-collector skill with a browser-capability adapter contract.
- Optional dual output (Markdown plus PDF) for the evidence report.
- Linking collected evidence into the tracker issue or PR comment by default.
- A per-run waiver that remembers "do not ask again for this workflow type".
- Evidence indexing across runs (a project-level evidence board).
