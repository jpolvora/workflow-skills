# Specification — Coordinated Prompt-to-Spec-to-Execution Lifecycle: 3-Phase Task Orchestrator & Canonical Tracking Skill

## Description

Ship a new on-demand coordinator skill **`ws-task-lifecycle`** for **prompt-driven** implementation (direct user task, not a Spec-to-PR run). Consumer repos today glue `ws-spec-index`, `ws-write-spec`, `ws-karpathy-guidelines`, `ws-senior-developer`, `ws-changelog`, and `ws-self-learning` in root `AGENTS.md`. That glue is skipped, so `index.PRD` never moves `[ ]` → `[~]`, slice specs are not created, and `FEATURES.md` / `PLAN.md` / `PRODUCT.PRD` stay stale after tests pass.

The skill is a **dispatch protocol** in `SKILL.md` (plus evals and catalog rows). It does not add a second FSM, `{plansDir}` tree, or ship/PR path.

**Phase 1 — Intake.** Read `{specsDir}/index.PRD` and repo-root `PLAN.md` when present. If the prompt is a product change and no matching `{specsDir}/{slug}.spec.md` exists, delegate to `ws-write-spec` (paths from `plans.specsDir`). Then set the index checkbox to `[~]` **before** product edits. Do not mkdir `{plansDir}` or write `step-00-*.spec.md`.

**Phase 2 — Implement.** Load karpathy + senior-developer. Run `verification.backendTest` when that alias is non-empty; otherwise record a skip.

**Phase 3 — Track.** Update existing canonical files in order: `FEATURES.md` → `PLAN.md` → `PRODUCT.PRD` → `index.PRD` (mark `[x]` + Done log where those conventions exist). Then `ws-changelog`, then `ws-self-learning`. Honor `tracking.canonicalFiles` when it is a non-empty array. Missing files: skip + note; continue.

**Not this skill:** `ws-spec-to-pr`, lite, `ws-multi-spec`, Always-applied autoload, inventing tracking files, spec-memo vaults, expanding `ws-sync-spec` into a tracking bus.

## Original Issue Context

```markdown
## Context & Motivation

In direct prompt-driven developer-agent workflows (such as in \spec-memo\ and consumer repos), work follows a structured 3-phase execution cycle:
1. **Phase 1: Intake & Spec Alignment (Pre-execution)**: Sync with \index.PRD\ and \PLAN.md\, locate or evaluate if a dedicated slice spec is needed (\.agents/specs/<slug>.spec.md\), and mark status as \[~] in progress\.
2. **Phase 2: Surgical Implementation & Verification**: Surgical modifications adhering to Karpathy diff hygiene, verifying exit proofs via tests (\npm test\).
3. **Phase 3: Completion, Canonical Tracking & State Update (Post-execution)**: Immediate multi-document tracking update in canonical order (\FEATURES.md\ → \PLAN.md\ → \PRODUCT.PRD\ → \index.PRD\ / \<slug>.spec.md\), followed by \ws-changelog\ and \ws-self-learning\.

Currently, the capabilities needed for this lifecycle are distributed across separate standalone skills (\ws-spec-index\, \ws-sync-spec\, \ws-karpathy-guidelines\, \ws-senior-developer\, \ws-changelog\, \ws-self-learning\). As a result, consumer repositories must write extensive glue prose in their root \AGENTS.md\ to coordinate these skills.

---

## Problem Statement

1. **No Cowork / Orchestrator Skill for Direct Tasks**: Full \ws-spec-to-pr\ pipelines generate multi-file plan trees (\.agents/plans/\), while direct single-turn / prompt tasks lack a lightweight coordinator skill that instructs loaded skills to cowork/hand off smoothly through the prompt → spec → execute → sync lifecycle.
2. **Risk of Spec Drift & Incomplete Tracking**: Without an explicit coordinator, agents frequently skip marking \[~] in progress\ in \index.PRD\, fail to split/update slice specs, or miss tracking updates in \FEATURES.md\ / \PLAN.md\ / \PRODUCT.PRD\ when tests pass.

---

## Proposed Approaches & Architecture

### Option A: Dedicated Task Lifecycle Orchestrator Skill (\ws-task-lifecycle\ or \ws-spec-driven-task\)
Create a new coordinator skill that defines the 3-phase dispatch:
- **Intake Handler**: Checks \index.PRD\ and \PLAN.md\; if no spec exists and the task warrants one, delegates to \ws-write-spec\ / \ws-spec-format\; transitions status in \index.PRD\ from \[ ]\ to \[~] in progress\.
- **Execution Guard**: Binds \ws-karpathy-guidelines\ + \ws-senior-developer\ during modification and test execution.
- **Sync & Completion Dispatcher**: Automatically triggers the canonical update order across tracking docs (\FEATURES.md\ → \PLAN.md\ → \PRODUCT.PRD\ → \index.PRD\ → \ws-changelog\ → \ws-self-learning\).

### Option B: Adapt & Expand Existing Skills (\ws-sync-spec\ + \ws-spec-index\)
- Enhance \ws-spec-index\ with pre-execution intake capabilities (\mark-in-progress\, auto-scaffold missing slice spec).
- Enhance \ws-sync-spec\ to not only update \*.spec.md\ bodies from code changes, but also coordinate the canonical post-execution tracking chain across \FEATURES.md\, \PLAN.md\, and \PRODUCT.PRD\.

### Option C: Autoloaded Meta-Skill / Coordinator Rule (\ws-cowork-lifecycle\)
- A lightweight skill added to the Always-applied autoload set that provides behavioral coordination guidelines across already-loaded skills without adding heavy pipeline overhead.

---

## Canonical 3-Phase Flow Specification

mermaid flowchart TD
    Prompt[User Prompt / Task Intake] --> P1[Phase 1: Intake & Spec Alignment]
    P1 --> CheckSpec{Spec exists in index.PRD / PLAN.md?}
    CheckSpec -- Yes --> AlignSpec[Review & Align Spec Instructions]
    CheckSpec -- No --> CreateSpec[Create .agents/specs/slug.spec.md & register in index.PRD]
    AlignSpec --> MarkProgress[Mark [~] in progress in index.PRD]
    CreateSpec --> MarkProgress
    MarkProgress --> P2[Phase 2: Surgical Implementation & Verification]
    P2 --> Exec[Karpathy-scoped edits]
    Exec --> Test[Verify exit proofs / npm test]
    Test --> P3[Phase 3: Completion & Canonical Tracking Sync]
    P3 --> S1[1. FEATURES.md: mark [x]]
    S1 --> S2[2. PLAN.md: append to Done log]
    S2 --> S3[3. PRODUCT.PRD: append to Done log]
    S3 --> S4[4. index.PRD / spec.md: mark [x] done & append Done log]
    S4 --> S5[5. ws-changelog & ws-self-learning]

---

## Next Steps & Questions for Feedback

1. Which architectural pattern is preferred: a new coordinator skill (Option A) vs enhancing existing skills (Option B) vs an autoloaded meta-skill (Option C)?
```
