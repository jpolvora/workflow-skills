# Companion — us-509 (ac_ledger link multi-AC commit linkage)

Decision record for `.agents/specs/pending/0179-us-509.spec.md`. Read it when implementing or reviewing AC1–AC15: it holds the product choices the acceptance criteria encode but cannot justify on their own, and it records where this spec stops.

## Feature Boundary

**In scope**

- Argument consumption for the **target lists** of `ac_ledger.cjs link`: `--ac` and its sibling `--negative` accept a space-separated id list in addition to the repeated-flag form (`ac_ledger.cjs:74-97`, `:271-277`).
- Target resolution semantics for one invocation: deduplicated union of both accepted forms, terminated by the next `--`-prefixed token (`:273-274`, `:342-343`).
- All-or-nothing application: every named id is validated against the ledger before the first mutation, an unknown id fails non-zero naming it, and nothing is persisted on failure (preserves the measured behavior of `ac_ledger.cjs:342`, `:354-356`, `:518-523`).
- The loud fallback branch the issue's *Expected* section allows: non-flag tokens that no flag consumed fail the invocation non-zero, naming the first offending token, instead of being dropped (`:84`, `:96`, `:867`).
- The `link` usage text, which must name both accepted `--ac` forms while keeping its flag list and `Example:` line (the `link` case of `ledgerHelpText`, `:825-840`).
- Regression coverage in the existing suites: `test/test-ac-ledger.js` (link/score fixtures, schema validation) and `test/test-script-ux-golden-path.js:52-72` (help lock), plus regenerated integrity (`bin/skill-integrity.json:601`).

**Out of scope (deferred, not rejected)**

- Space-separated grouping for evidence flags (`--file`, `--test`, `--commit`, `--verdict`, `--finding`, `--files-touched`); they keep one value per flag occurrence and now fail loudly on leftovers.
- Any change to `score` / `verify` exit codes or to the meaning of `scoreState.errors[]`.
- The G2 caller's warn-and-continue posture on a failed link (`commit_g2_code.cjs:161`).
- The operator documentation that prescribes the repeated form (`ws-implement-tasks/SKILL.md:54`, `gates.md:229`, `:233`), which stays correct because that form keeps working.
- The other ~99 helper scripts that duplicate `parseArgs`; only `ac_ledger.cjs` is corrected here.

## Implementation Decisions

### D1 — Which branch of the issue's *Expected* is the primary behavior (two valid options)

The issue leaves a real product choice: attach the commit to every named AC, or fail loudly naming that multi-AC linkage is unsupported.

- **Option A — accept the short form and attach to every named AC (chosen).** One `--ac AC1 AC2 AC3` links all three rows. Consequence: the documented short form starts working, the "Workaround" loop stops being necessary, and every agent-authored invocation that follows the usage text becomes correct. Cost: target-list consumption is no longer strictly one value per flag occurrence, so the parser needs an explicit terminator and the leftover-token guard.
- **Option B — keep one value per flag and fail loudly on extras.** `--ac AC1 AC2` exits non-zero telling the caller that multi-AC commit linkage needs repeated flags. Consequence: the smallest possible behavioral delta, but the usage text (`[--ac ACn ...]`, `:826`) must be narrowed in the same change, every multi-AC agent invocation burns a retry round at exactly the step that is already gate-sensitive, and the issue's own reproduction stays a failure with a clearer message.

**Rationale for A.** The interface as documented already promises the short form, and the only in-repo caller is unaffected either way (`commit_g2_code.cjs:157` builds the repeated form and keeps working under A). Option B would leave a documented invocation failing, which converts a silent defect into a loud annoyance rather than a fix; the loudness that B provides is not lost under A, because the unconsumed-token guard (D3) makes every *unsupported* grouping loud. Under A, "silently applied to one target" becomes impossible in both directions: supported lists apply fully, unsupported lists fail.

### D2 — Where multi-value consumption applies, and where it stops

Multi-value consumption is limited to the two **target lists** of `link` (`--ac`, `--negative`), which share one code path and one gate consequence. Values are consumed until the next token that starts with `--`, mirroring the existing value-optional check for `--productFailure` (`:89-92`). Evidence flags keep their per-occurrence semantics: a caller that lists several `--file` values in one flag gets a hard error (D3), not a silently shortened evidence set. Restricting the change to target lists keeps payload semantics untouched and makes the blast radius one code path instead of the whole flag set.

### D3 — The loud guard for tokens no flag consumed

After parsing, any non-flag token other than the subcommand is an error naming the first such token; the helper writes nothing. This is the materialized form of the issue's second branch, applied where branch A does not reach: it removes silent truncation as a *possible* outcome for every flag family, including the evidence flags and any future flag, without changing their accepted syntax. Its cost is explicit and intended: an existing invocation that relied on truncation (for example `--test a b`) now fails instead of quietly linking half its evidence. That trade is accepted because such an invocation was already producing a wrong ledger with a green exit code, and the score gate would have reported the shortfall as a deficiency on some other AC.

### D4 — Atomicity is preserved, not redesigned

The measured baseline already validates ids inside the loop and writes the ledger once afterwards, so a rejected link leaves the file byte-identical (SHA256 and `revision` unchanged). The fix keeps validate-then-write ordering: the new multi-value resolution must not add a write before the whole target list is validated, and the single revision bump per successful call (measured) must stay at one. No new failure contract is invented; the existing one is extended to the new input shape.

### D5 — Duplicate ids collapse; unknown ids fail

A repeated identical id (`--ac AC1 --ac AC1 AC2`, or `--ac AC1 --ac AC1 AC2`) resolves to one target. A duplicate is not an input error, and rejecting it would contradict the union semantics that make mixing both accepted forms predictable. The negative scenarios still assert the observable consequence: exactly one commit entry per row, no duplicated `linkEventIds` values, one revision bump. Unknown ids stay fatal and atomic (D4).

### D6 — The usage text changes additively, and only there

`link --help` is phrase-locked by `test/test-script-ux-golden-path.js:52-72` (flag list plus `Example:` per subcommand), so the usage line gains the space-separated form without dropping `--ac`, `--commit`, `--score-boundary`, or the example. Documentation that prescribes the repeated form is not edited: after this change both forms are correct, and rewriting working instructions would expand the diff for no behavior gain.

### D7 — Why the acceptance signal is `scoreState.errors[]`, not an exit code

`score --boundary pre-step6` exits **0** while listing `${row.id}: product commit linkage required before step 6` in `scoreState.errors[]` (`:687`), and `commit_g2_code.cjs:161` downgrades a failed link to a `WARN` and continues. The complete failure is therefore observable as a *derived error entry*, and the fix's success is that the entry disappears for every named AC (AC12). Adding a non-zero exit for linkage errors would change a contract that callers and the verify loop already read, so it is out of scope.

### D8 — Test placement

Assertions extend the existing suites so no `test/test-suites.json` registration is needed (`:364` already lists `test/test-ac-ledger.js`). A new test file is acceptable only if it is registered in the same change; the DoR row states the obligation either way.

## Deferred Ideas

- **Batch event-id ergonomics.** One `link` call now stamps N ACs with a single `--event-id`, which is exactly what the G2 caller wants (`g2-commit-<sha>`). A per-target event id (for example `g2-commit-<sha>#AC2`) would make partial re-links and audit trails more precise, and would remove the last reason for the per-AC loop. Deferred because event-id semantics feed `linkEventIds` dedup and the already-applied skip path, so it needs its own spec.
- **A `--dry-run` / resolve-only mode** that prints the resolved target list and the flags it would apply before writing, so an agent can validate a long invocation cheaply. Deferred: the new unconsumed-token guard already makes the dangerous case loud, and a dry-run flag adds surface for every subcommand.
- **Space-separated grouping for evidence flags**, so `--file a:L1-L2 b:L3-L4` works instead of failing. Deferred to keep the payload vocabulary one-value-per-flag; the guard makes the current behavior explicit rather than silent.
- **Comma-separated ids** (`--ac AC1,AC2`) as a third dialect. Deferred: two accepted forms already cover short and long invocations, and a third dialect multiplies parsing rules for no new capability.
- **Making the already-applied event-id skip a strict no-write.** It currently prints the `NOTICE` and still rewrites the ledger, bumping `revision` (observed 3 → 4). Deferred because revision accounting is read by other gates and this is unrelated to the reported failure class; payload idempotency is what the spec pins.
- **Fail-fast in `commit_g2_code.cjs`.** A failed link is recorded as a `WARN` and the run continues (`:161`), so the linkage error only surfaces one gate later. Making the G2 caller stop on a failed link is a separate hardening decision about step 5/6 blast radius.
- **One shared flag-parsing module for the helper family.** `function parseArgs` is duplicated in ~99 scripts under `.agents/skills/**/scripts/`, and `ac_ledger.cjs` is only one instance of the same silent-truncation shape. A shared parser with leftover-token rejection would retire the whole class; deferred because it is a cross-skill refactor with its own compatibility surface.
- **Applying the leftover-token guard to every helper now.** The narrow version here fixes the reported command; a harness-wide sweep of the other duplicated parsers is a follow-up rather than part of this spec.
