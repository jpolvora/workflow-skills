# Specification — [Spec] Create a new skill ws-spec-to-issue

## Description

Add a packaged skill `ws-spec-to-issue` that turns a free-text feature description into an agentically refined, anonymized **tracker item** (GitHub issue or Azure DevOps User Story) **without writing any local spec file or touching git**. It is the inverse-direction companion of `ws-spec-write` plus the provider import path: describe an idea, let the skill reformulate it into a spec-shaped body, anonymize it, and create the remote issue; later `ws-spec-from-provider` / provider `fetch-to-spec` re-imports it into a local spec of record when the team is ready to implement.

Rationale: an idea often arrives while a workflow is running in the same repository. Writing a local `*.spec.md` would dirty `git status` and can interleave with the running workflow's commits. Routing the idea to the tracker keeps the working tree clean and defers implementation.

Architecture touchpoints: new skill folder `{skillsRoot}/ws-spec-to-issue/` (SKILL.md + helper `.cjs` if needed); the active provider `create-issue` intent (GitHub `ws-spec-provider-github/scripts/create_issue.cjs`, Azure DevOps `ws-spec-provider-azure-devops/scripts/create_issue.cjs`); config resolution for `providers.active` (`.ws/config.json`); the source-anonymization rule (hub `AGENTS.md`); both dependency manifests; package integrity and version; router/doc surfaces.

## Acceptance Criteria

### Skill presence and registration

- AC1: A packaged skill `ws-spec-to-issue` exists at `{skillsRoot}/ws-spec-to-issue/SKILL.md` with valid `name`, `description`, and an `invocation_names` entry (e.g. `/spec-to-issue`, `ws-spec-to-issue`).
- AC2: The skill is registered in both `bin/skill-dependencies.json` and `.agents/skills/ws-shared/runtime/skill-dependencies.json` under the specs package with an explicit `dependencies` entry naming its provider/`ws-spec-write` callees.

### Tracker resolution and auth

- AC3: The skill resolves the active tracker from `.ws/config.json` (`providers.active` `github`|`azure-devops`; else an enabled `issueTrackers.*`; else `project.repoUrl` host). Active `local` with no tracker fallback **STOPs** with a named error and never writes a local spec.
- AC4: The skill runs the active provider `validate-auth` before any mutating call; auth failure **STOPs** with the provider remediation and performs no silent fallback.

### Payload shaping and anonymization

- AC5: The skill builds a spec-shaped payload (title + body carrying Description, atomic testable Acceptance Criteria, and Out of Scope) by **agentic reformulation** of the free-text description, reusing the `ws-spec-write` reformulation protocol — not a verbatim copy of the input.
- AC6: The payload is anonymized before creation: no private consumer project names, no absolute local paths, no hostnames, no secrets, and no customer data; the description states the failure class or feature generically when the input quoted private context.

### Creation and side-effect safety

- AC7: The skill creates the item via the active provider `create-issue` intent (GitHub `create_issue.cjs`; ADO `create_issue.cjs --type "User Story"`), passing the body through `--body-file` to avoid inline-quoting hazards, and prints the created id and URL.
- AC8: A successful run leaves **no** local artifact: no `{specsDir}` spec of record, no `{plansDir}` folder, no `git add`/commit; `git status --porcelain` is byte-identical before and after the run.
- AC9: `--dry-run` prints the resolved tracker, title, and body and creates nothing; it exits 0.
- AC10: The skill never embeds tokens; the token is read only from the configured env var by the provider script, any temp body file is created outside the tracked tree and removed after the call, and nothing sensitive is echoed.

### Failure handling and round-trip

- AC11: A creation failure (auth, network, validation, or provider non-zero exit) is reported with the provider error and a non-zero exit; no partial or half-written local artifact remains.
- AC12: The created item round-trips: running `ws-spec-from-provider` (or provider `fetch-to-spec`) on the new id produces a valid spec of record that passes `validate_spec.cjs --mode=authoring` (or `--mode=compat` when the body lacks closure tables).

### Docs, integrity, and harness

- AC13: The new skill is routed/indexed in `AGENTS.md`, `.ws/AGENTS.md`, `README.md`, `FEATURES.md`, `CATALOG.md`, `autoload.md`, `docs/llms.txt`, and the generated site; `ws-check-harness` Phases 0–5c report 0 findings and `test/test-harness-clean.js` reports 0 findings.
- AC14: `npm run generate-integrity` + `npm run verify-integrity` exit 0 and `package.json` `version` / `packageVersion` are bumped once for the release PR.

## Notes

- Reuse, do not fork: the anonymization wording mirrors hub `AGENTS.md` § Source anonymization; the body-shaping mirrors `ws-spec-write` § Agentic Reformulation & Enhancement Protocol; the network call delegates to the provider `create-issue` intent — no provider CLI recipe is embedded in the skill.
- Keep the working tree clean by design: the body is passed via a temp `--body-file` created outside the repository root and deleted after the call.
- Provider parity: both `ws-spec-provider-github` and `ws-spec-provider-azure-devops` implement `create-issue`; the skill selects one by `providers.active` and must not load both provider bodies.
- Optional `--label` passthrough to the provider intent is allowed but must remain provider-neutral in the skill prose.
- The skill is standalone (config-dependent) and may run while a workflow owns the repository; it must never stage, commit, stash, or reset.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Writing any local `{specsDir}` spec or `{plansDir}` artifact | The issue's core requirement is to keep the working tree untouched; local write is the alternative being avoided |
| Implementing the feature after creating the item | The issue defers implementation to a later import + workflow run |
| Auto-importing the created item into a spec | Reverse direction is owned by `ws-spec-from-provider` / provider `fetch-to-spec` |
| A new tracker API client | Provider `create-issue` intents already exist; the skill composes them |
| De-duplicating or updating an existing issue | Not requested; the issue describes creating a new item only |
| A local queue/file cache of pending ideas | Would reintroduce the git-status pollution the issue avoids |

- `node {skillsRoot}/ws-spec-to-issue/SKILL.md` exists and the skill is listed by `ws-check-harness`; both dependency manifests contain the new id.
- `node .agents/skills/ws-spec-to-issue/... --help` (or the documented entry) exits 0 and prints usage including `--dry-run`.
- A `--dry-run` invoke prints the resolved tracker, title, and reformulated anonymized body and creates nothing; `git status --porcelain` is unchanged.
- A live invoke prints the created item id and URL; the provider `create-issue` intent exits 0.
- Round-trip: `ws-spec-from-provider` on the new id writes a `{specsDir}` spec that passes `validate_spec.cjs --mode=authoring` (or `--mode=compat`).
- `npm run test` and `test/test-harness-clean.js` (0 findings) exit 0; `npm run verify-integrity` exits 0.

### Negative & Failing Test Scenarios

- `providers.active: local` with no enabled tracker: the skill STOPs with a named error and writes no file; a test asserts no `{specsDir}` or `{plansDir}` output.
- Auth missing/invalid for the resolved tracker: the create step fails with the provider remediation and a non-zero exit; no item is created and no local artifact remains.
- Input containing a private project name, absolute path, or hostname: the built payload must not contain it; a test asserts the anonymizer strips it before the create call.
- Provider `create_issue.cjs` returns non-zero (network/validation): the skill reports the error, exits non-zero, and leaves `git status --porcelain` unchanged.
- `--dry-run` accidentally performing a create: the payload print is the only output and no provider mutation occurs (negative assertion on the provider dry-run path).
- Running the skill inside an active workflow: no `git add`/commit/stash/reset is issued and the tree stays clean.
