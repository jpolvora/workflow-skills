# Specification — [ws-monitor ms-20260919T043606Z] Step 3 completed without exec artifact; Step 4 completed with empty filesTouched (live us-354 run)

## Description

Observed during read-only monitoring of a live multi-spec batch run (4 standard items; first child in progress at the verify step):

- **Signal 1:** Step 3 is marked completed, but the expected `step-03-<slug>.plan.exec.md` artifact is absent from the plan directory. This pattern is shared by many completed runs, while other runs do produce the file — so either the artifact should not be required in sequential (non-DAG) mode, or the step should not be marked completed without writing it.
- **Signal 2:** a completed mutating Step 4 reported empty `filesTouched` in telemetry (`telemetry.jsonl`) — i.e. the subagent handoff did not record touched files.

Expected contract: a completed step has its mandatory artifact on disk; a completed mutating step reports non-empty `filesTouched` in telemetry.

Evidence (file names only): `ws-spec-multi/ms-20260919T043606Z.state.md` queue, `us-354/step-03-us-354.plan.exec.md` (absent), `us-354/telemetry.jsonl`, `us-354/us-354-20260919T043606Z.state.json`.

Decide per signal whether the fix is contract-side (require the artifact / non-empty handoff before marking completed) or definition-side (artifact not required in sequential mode; empty `filesTouched` legal when the step genuinely touched nothing), then implement the chosen semantics plus a monitor check that flags the violation class.

System boundaries: step-completion contracts (`ws-plan-to-tasks` Step 3 exec artifact, `ws-implement-tasks` Step 4 handoff/telemetry) and `ws-monitor` read-only detection. Architecture touchpoints: step-output DONE envelopes, telemetry writers, state `status: completed` transitions, and the monitor snapshot rules. No provider or SCM changes.

## Acceptance Criteria

- AC1: The Step 3 exec-artifact rule is unambiguous: either sequential mode requires `step-03-<slug>.plan.exec.md` before `completed`, or the artifact is declared optional in sequential mode and the state/monitor no longer treat its absence as a signal — verified by reading the owning skill contract plus a state-machine test.
- AC2: A mutating Step 4 cannot report `completed` with empty `filesTouched` unless the step genuinely modified nothing (explicit no-op declaration); otherwise completion is withheld or flagged — verified by a telemetry/handoff test.
- AC3: `ws-monitor` flags both violation classes (missing mandatory artifact on a completed step; empty `filesTouched` on a completed mutating step) in its snapshot — verified by fixtures reproducing both signals.
- AC4: Existing historical runs without the artifact are classified (grandfathered vs violation) so the monitor does not flood on old batches — verified by a compat-mode fixture test.

### Design Intent

- The `step-03-*.plan.exec.md` artifact convention grew per-mode: DAG/exec-group runs produce it as a task ledger, while sequential runs often skip it — the `completed` transition never distinguished the two. Whether this is an accidental gap (missing write) or intentional (artifact only meaningful with parallel groups) is exactly what AC1 decides; `git log -p -S "plan.exec" -- .agents/skills/ws-plan-to-tasks` will show which mode introduced the file.
- Empty `filesTouched` on a mutating step is presumed accidental (handoff omitted the list); the no-op carve-out in AC2 exists because a step can legitimately complete with zero file changes (e.g. verification-only retries).
- Greenfield detection rules in `ws-monitor`; contract-side fixes in the owning step skills.

## Notes

- Prefer the stricter contract (require artifact / non-empty handoff) unless evidence shows sequential mode intentionally omits the file — silent completion without evidence is the failure class behind several recent re-dispatch incidents.
- Keep the monitor check read-only: flag from state + directory listing + telemetry, never by writing markers into the observed run.
- Anonymize run evidence in reports: file names and signal classes only, no session contents or host paths.
