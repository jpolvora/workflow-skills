# us-507 context — ws-monitor state-less run discovery

Companion to `.agents/specs/pending/0177-us-507.spec.md`. Records the product choices the issue leaves open so the plan does not have to re-litigate them.

## Feature Boundary

- **In:** `ws-monitor` discovery of a top-level `{plansDir}/{name}/` run directory that holds step artifacts and no `*.state.json` / `*.state.md`; a `run-without-state` finding with window-bounded severity; inclusion in `workflowCount` / `activeCount` so `--until-terminal` neither misses a fresh run nor hangs on an abandoned one; the skill's signal documentation.
- **Out:** writing or repairing state, deriving step/score/telemetry from artifacts, changing `missing-child-state`, recursive scans of `worktrees/` or `.runtime/`, back-filling `{plansDir}/index.json`, and any auto-filing behavior beyond the existing `--open-issue` proposal path. Full table in the spec's `## Out of Scope`.

## Implementation Decisions

- **D1 — Selection key for `--slug`.** A state-less directory is selected by plan directory name; state-backed runs keep us-464's state-derived selection unchanged. *Rejected:* excluding state-less directories from scoped snapshots. The repro sketch scopes `--slug demo` at a directory with no state, so exclusion would hide the run exactly where the issue observes it.
- **D2 — `--workflow-id` never selects a state-less directory.** *Rejected:* synthesizing a run id from the directory name. The observer would report an identity the run never recorded, and machine selectors are also used for resume-style lookups where a fabricated id is worse than no match.
- **D3 — Counting is window-bounded.** A state-less run inside the stall window counts toward `activeCount`; an older one stays visible as `info` and does not. *Rejected:* counting every state-less directory (an unattended `--until-terminal` would never exit on an abandoned directory) and counting none (the reported defect survives, because a fresh run would still read as finished).
- **D4 — Evidence is the canonical top-level `step-NN-` prefix**, not a hand-listed artifact set, and not the nested `.runtime/` liveness markers. *Rejected:* enumerating the full per-step name list from `expectedArtifacts()` — that list is per-pipeline and state-dependent, and a hard-coded copy would be the parallel detector the issue rules out.
- **D5 — The record does not fabricate run state.** `statePath` stays null, step and verification fields stay unknown, and the newest artifact is carried as repo-relative evidence. *Rejected:* reporting the highest `step-NN` seen as `currentStep` — artifact numbering proves activity, not completion.
- **D6 — Stale state-less runs stay non-actionable.** `info` findings do not enter `actionableFindings()`, so an old abandoned directory cannot keep producing `--open-issue` proposals; fresh runs remain actionable by design because a live run without state is a genuine defect signal.

## Deferred Ideas

- Back-filling state-less runs into the state-derived `{plansDir}/index.json` registry, or making that registry artifact-aware.
- An ignore list (`monitor.ignoreDirs`-style) for deliberately state-less scratch or benchmark directories.
- Extending the signal to `{plansDir}/{runId}/` multi-spec child directories that leave no child state but do leave artifacts.
- An offline audit (harness check) that reports state-less directories across the whole plans root, beyond the live observer.
