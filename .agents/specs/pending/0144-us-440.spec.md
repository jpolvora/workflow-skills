# Specification — skillLoader: adopt token-centered skill loading at inline body-load sites

## Description

`{skillLoader}` is the eighth host-capability token, introduced by spec `0136` (`completed/0136-skill-loader-host-capability.spec.md`). Its canonical procedure lives in exactly one normative place: `.agents/skills/ws-shared/runtime/host-capability-tokens.md` § Skill-load procedure (bound native loader when the host declares one, else `{skillsRoot}/ws-<id>/SKILL.md` via `{readFile}`, with an already-loaded check and `skill-load | {id} | {loaded|read}` telemetry). The token/pre-map/probe surface is `host-tool-map.json` + `probe_host_capabilities.cjs`, and enforcement is `ws-check-harness` Phase 5a `check_skill_load.cjs`.

The gap: several skill bodies load another skill's **body inline in the same session** without citing `{skillLoader}` or delegating to the canonical procedure. The Phase 5a gate deliberately exempts these sites because the prose states *what* to load, not *how*; consequently each site silently re-invents the load, and only some sites carry the already-loaded dedupe and `skill-load` telemetry. This is a consistency/observability defect, not a runtime correctness bug.

This spec converts the in-scope inline body-load sites to token-centered wording that cites `{skillLoader}` and links the canonical procedure, while leaving two out-of-scope classes untouched: (1) `dispatch-agent` orchestration (standard orch → step skills) where the subagent loads its own body and `{skillLoader}` is the wrong token; (2) script-level delegation where no skill body is read (e.g. `ws-configure-project` → `ws-spec-memo` `.cjs`, `ws-ship-pr` → `ws-secrets-leak-review` hook, `ws-goal-fix-pr` → `ws-goal-loop` helper).

Architecture touchpoints: skill prose under `.agents/skills/ws-*`; the shared runtime contract `ws-shared/runtime/host-capability-tokens.md`; the optional `check_skill_load.cjs` extension and its fixtures; package integrity and version. Change is doc-only plus at most a bounded gate extension.

- AC1: `ws-task-lifecycle/SKILL.md` load sites cite `{skillLoader}` with the canonical-procedure link: invoke `ws-spec-write`, invoke `ws-spec-index`, load `ws-senior-developer`, and invoke `ws-changelog` then `ws-self-learning`.
- AC2: `ws-spec-manager/SKILL.md` cites `{skillLoader}` with the canonical-procedure link in the subcommand → target `ws-spec-*` mapping and in § Dispatch & Delegate.
- AC3: `ws-spec-write/SKILL.md` cites `{skillLoader}` with the canonical-procedure link when delegating to `ws-spec-provider-local`.
- AC4: `ws-code-review/SKILL.md` cites `{skillLoader}` with the canonical-procedure link when writing via `ws-self-learning` and when running the optional `ws-fable-judge` audit.
- AC5: `ws-ship-pr/SKILL.md` cites `{skillLoader}` with the canonical-procedure link for the `ws-fable-judge` row and for security via `ws-secrets-leak-review`.
- AC6: `ws-goal-fix-pr/SKILL.md` cites `{skillLoader}` with the canonical-procedure link when wrapping `ws-fix-pr` in `ws-goal-loop` and when applying the `ws-goal-loop` helper.
- AC7: The reference shape already shipped at `.agents/skills/ws-spec-list/ACTIONS.md` ("load `ws-spec-to-pr[/lite]` via `{skillLoader}` (canonical skill-load procedure)") is the template; converted sites match that phrasing shape (token + link), not a paraphrase that drops the token or the link.
- AC8: No converted site duplicates the procedure text; each delegates by link. `check_duplicates.cjs` (Phase 5a) remains green after the edits.

### Out-of-scope preservation

- AC9: `dispatch-agent` orchestration sites (e.g. `.agents/skills/ws-spec-to-pr/STEP-DISPATCH.md`, `.agents/skills/ws-spec-to-pr-lite/SKILL.md`) are unchanged and remain exempt; the PR records that exemption with the reason "subagent loads its own body; `{skillLoader}` is the wrong token".
- AC10: Script-level delegation sites (`ws-configure-project` → `ws-spec-memo` `.cjs`, `ws-ship-pr` → `ws-secrets-leak-review` hook, `ws-goal-fix-pr` → `ws-goal-loop` helper) are unchanged and remain exempt; the PR records that exemption with the reason "no body read".

### Optional gate hardening

- AC11: If `check_skill_load.cjs` is extended, it flags a bare `Load`/`invoke` of a `ws-<id>` where the wording means an in-session body load, and it consults an explicit allowlist for `dispatch-agent` orchestration, script-level delegation, and the canonical doc. No new false positive is emitted for the allowlisted classes.
- AC12: Any `check_skill_load.cjs` extension ships positive and negative fixtures under the existing test fixtures location; the negative fixture is a synthetic bare-load site that must fail, the positive fixture is an allowlisted site that must pass.

### Verification and package integrity

- AC13: `node .agents/skills/ws-check-harness/scripts/check_skill_load.cjs` (all skill docs) exits 0, `npm run test` (`verification.backendTest`) exits 0, and `ws-check-harness` Phases 0–5c report 0 findings at the package root.
- AC14: `npm run generate-integrity` followed by `npm run verify-integrity` both exit 0; if the change ships as a release PR, `package.json` `version` and `packageVersion` in `bin/skill-dependencies.json` are bumped once (strictly above the merge-base).

> ## Context
>
> `skillLoader` is the eighth host-capability token (`{skillLoader}`), added by spec 0136. Its canonical procedure lives in exactly one normative doc:
>
> - `.agents/skills/ws-shared/runtime/host-capability-tokens.md` § Skill-load procedure (bound native loader when declared, else `{skillsRoot}/ws-<id>/SKILL.md` via `{readFile}`, with an already-loaded check and `skill-load | {id} | {loaded|read}` telemetry).

> ## Problem
>
> Several skills load another skill **body inline in the same session** without referencing `{skillLoader}` or delegating to the canonical procedure. The gate intentionally exempts these, because the wording states *what* to load, not *how* — so the divergence is invisible today and each site re-invents the load implicitly.

> Two patterns are **not** in scope and must stay exempt:

> ## Files to edit (inline body-load sites)

> | `.agents/skills/ws-task-lifecycle/SKILL.md` | 29, 31, 38, 59 | invoke `ws-spec-write`; invoke `ws-spec-index`; **Load** `ws-senior-developer`; invoke `ws-changelog` then `ws-self-learning` |

> ## Proposed acceptance criteria
>
> - AC1: Each in-scope inline body-load line cites `{skillLoader}` and links the canonical skill-load procedure in `host-capability-tokens.md` instead of naming a bare load.
> - AC2: `dispatch-agent` orchestration sites and script-level delegation sites remain unchanged (documented as exempt in the issue/PR).

### Design Intent

- Not a bugfix; skip `git log -p -S`. The design intent of spec `0136` was to make skill loading host-neutral with a single canonical procedure and already-loaded dedupe. This spec completes adoption at the sites the Phase 5a gate intentionally leaves exempt, without changing the token, the procedure, or the gate's failure semantics.
- Constraint to keep: `{skillLoader}` is for in-session body loads only; `dispatch-agent` (subagent loads its own body) and script-level delegation (no body read) are semantic mismatches and must not be converted.

## Notes

- Wording template (from `ws-spec-list/ACTIONS.md`): "load `ws-<id>` via `{skillLoader}` (canonical skill-load procedure)" — token plus link, no restated how-to.
- `ws-ship-pr/SKILL.md` also references `PREPARE-CHECKLIST.md`, which is a companion file of the same skill, not a `ws-*` skill body; convert only the `ws-fable-judge` / `ws-secrets-leak-review` rows to the token shape and leave companion-file reads as ordinary references.
- Keep the change minimal: one line per site where possible; do not reformat surrounding prose.
- If the optional gate extension (AC6/AC7) expands scope beyond a patch, split it into a follow-up spec; the doc-only conversion (AC1–AC5) is independently shippable.
- Host neutrality: do not name host products as loader values; the token resolves through `host-tool-map.json` / the bound native loader.

## Out of Scope

| Feature | Reason |
|---------|--------|
| Converting `dispatch-agent` orchestration sites | The subagent loads its own body; `{skillLoader}` is the wrong token for that class |
| Converting script-level delegation sites | No skill body is read; there is nothing to load |
| Changing the autoload set in `autoload.md` | The issue explicitly lists this as a non-goal; adoption is orthogonal to what autoloads |
| Adding native skill-loader tool names to the pre-map | Host-neutral package; coverage stays additive via `--declare` |
| Changing dispatch-tier, user-gate, or orchestrator semantics | Out of scope by the issue non-goals |
| A mandatory (always-on) gate extension | AC4/AC6 are optional; conversion must not depend on the gate change |
